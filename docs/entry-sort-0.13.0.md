# 입력 정렬과 바코드 행 보존 0.13.0

구매 입력의 정렬을 한 가지 기준에서 최대 세 가지 기준으로 확장했다. 또한 바코드 개별 입력 또는 A/B/A 순서 입력으로 생기는 반복 품목 행을 저장할 때 기존 전표의 행 식별자를 사용하도록 보완했다. 0.12.0에서는 해당 초안의 중복 품목 저장이 거절될 수 있었다.

## 원본과 구현

원본 구매입력 E040303의 정렬창은 순서·정렬기준·정렬방법 세 열과 세 우선순위, 기본값 없음, 적용 F8·닫기, Option의 기본값설정을 표시했다. 기준 선택 목록에는 품목코드·품목명·단위·BOX·수량·단가(vat포함)·공급가액·부가세·합계·적요·시리얼/로트가 있었다. 기준을 선택하면 방향 버튼이 활성화됐고 클릭할 때 방향 아이콘이 바뀌었다. 설정창 안의 선택만 확인한 뒤 적용·기본값 저장 없이 닫았다.

REA 근거는 앞서 실제 분석한 FM080P_02와 contentsloadslip sort 위젯의 소스 위치·SHA를 재사용한다. 일반 적용은 빈 기준과 중복 열을 거절하며 부모에게 기준/방향 쌍을 전한다. 실제 grid 비교 함수·원본 정렬 기본값 보관은 미확인이다.

우리 정렬은 현재 화면에 보이는 열 중 계산 가능한 코드·품목명·규격·단위·수량·단가·VAT포함단가·공급가액·부가세·합계·적요·거래처 코드/명칭을 제공한다. BOX와 시리얼, 추가 양식 계산 열은 이번 범위에 포함하지 않는다. 없는 열을 미리 채워 놓지 않는다. 문자 한국어/숫자 비교와 동률일 때 기존 순서 보존은 자체 정책이다. 수량·금액은 숫자로 비교하며 금액은 기존 전표의 반올림·반품 배분 함수를 사용한다. 기준만 선택했을 때 전표는 변경되지 않고, 적용 F8에서 행 순서만 바뀐다. 빈 기준·중복·권한 부족·미리보기 이후 전표/마스터 변경은 적용을 차단한다.

## 반복 바코드 행과 연결 보존

반복 품목 행에는 기존 lineId 계약으로 식별자를 부여한다. 원래 식별자는 그대로 유지하며 새 값은 현재 행들과 충돌하지 않게 생성한다. 핵심 저장기·반품 연결·백업 검증이 이미 지원하던 필드를 이용하므로 새 스키마나 마이그레이션은 없다. 원본 서버의 행 번호 규칙과 동일하다는 주장은 하지 않는다.

후속 전표가 있고 행 구분이 없던 예전 전표에는 새 식별자를 자동으로 붙이지 않는다. 기존 연결이 깨질 수 있으므로 개별 행 추가를 거절하고 새 전표 입력을 안내한다. 새 전표의 A/B/A 행 저장 → JSON 백업 검증 → 세 번째 A만 부분 반품 → 행별 잔량 보존을 합성 자료로 검증했다. 실제 구매 화면에서 바코드 Enter 입력 → 세 행 유지 → 코드 내림차순 정렬 → 저장 → 백업 검증도 통과했다. 바코드 이후 일반 행 추가·품목 선택·붙여넣기로 추가한 행도 식별자를 보완해 저장 가능함을 검증했다. 원본 업무 전표는 저장하지 않았다.

## 합격 조건과 남은 범위

관련 검사 38개가 통과했으며 최종 전체 검사와 배포 파일 결과는 `evidence/global-rea-20261018/entry-sort/validation.json`에 기록한다. 정렬 기본값 저장, 원본 grid 문자열 비교 세부 규칙, BOX/추가수량 환산, 원본 저장 후 분기 및 전자결재·지급은 계속 대조한다. 전역 759개 경로의 기준과 아직 안내 카드인 487개 범위는 그대로다. 호스팅 로그인 후 업무·실휴대폰/스캐너 검증은 미실행이다.

추가로 현재 DOM의 공개 footer 원문 2개·147,317B를 실제 REA6.4.0으로 분석했다. 신규 파싱/의미 분석은 모두 완료했고 원문은 실행하지 않았다. 누적 SHA 중복 제거 원문은 66개·9,628,494B, 정적 완전65/부분1·의미 완전64/부분1/시간 중단1이다. 모든 신규 호출 2,088개는 미해결이며 서버 저장 결과와는 구분한다. 내용유지는 저장 전표의 수정 모드 재개, 신규는 저장 키를 참조한 신규 모드 재진입을 요청한다. 신규 필드 초기값과 페이지별 재정의는 미확인이다. 직접지급은 별도 지급창이고 보류는 별도 서버 쓰기다. 이 분기들은 이번 배포에서 임의로 활성화하지 않았으며 다음 대조 대상이다.
