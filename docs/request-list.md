# 발주요청조회 원본 대조와 구현 0.7.2

원본 E040315 화면을 직접 열어 관찰하고 공개 배포 JavaScript 4개를 REA 6.4.0으로 정적 분석했다. 이번 구현은 발주요청조회 목록의 배치와 기존 로컬 작업을 정비한 범위이며 발주요청 전체 기능의 원본 동등성을 의미하지 않는다. 기준 소스는 0.7.1 `df160b98e6f619afbae132028a5968ae771628c2`이고 새 작업 사본은 `/workspace/scratch/bb556d5a9f94/rea-request`다.

## REA 근거와 한계

정확한 URL·파일별 입력 SHA256·분석 지표·UI 관찰 목록은 `evidence/request-list-0.7.2.json`에 있다. 원본 코드/회사 자료/세션 URL은 dist에 포함하지 않는다. 원본 sources 폴더는 변경하지 않았다.

공개 원본 4개 전체 파일 합계 1,102,589B를 직접 라이브러리의 구문·의미 분석에 입력했다. 목록 페이지는 IGetInventorySetupProgram/IGetInventoryDataModelProgram에 위임하며 공개 usecase에는 GetInventorySetupAction·검색 상태·확인·삭제 API 식별자가 존재한다. 이는 해당 API를 직접 호출하거나 서버 규칙을 검증한 결과가 아니다. ConfirmInventory 액션은 confirm_type을, 주문관리 코드는 progress/progress_status를 별도로 다룬다. 현재 자체 단일 status 모델을 원본과 동일하다고 주장하지 않는다.

CLI application graph는 ps 소유권 확인의 `fatal library error, lookup self`에서 실패했다. 프로세스 소유권 보호는 변경하지 않았고, 대상 실행·자식 프로세스 없이 REA 원본 라이브러리의 직접 정적 분석으로 범위를 한정했다. 선택 파일의 구문 분석 완료와 ERP 전체 호출 그래프 완성은 다르다. 동적 this/외부 ProgramBuilder/비공개 서버 호출은 미확인이다.

## 검증과 보존

전체 자동 검사 530개(기존 521개+새 조회 검사 9개), 관련 상태·조회 17개를 확인했다. 브라우저에서는 supervisor의 가상 전표 전용 화면으로 하단 배치·접힌 검색·상태변경 저장·발주계획 변환 확인창/성공 안내를 확인했다. 실제 배포 앱 계정의 업무 검증 및 실휴대폰 검증과 구분한다. 프리뷰 fixture는 scripts에 있으며 Worker dist에 포함되지 않는다.

저장 스키마 v2와 기존 계산·상태·API 업무 모델은 유지한다. 원본 회사 전표의 저장·상태변경·취소·삭제·전송·설정 저장은 실행하지 않았다. 조회 열의 인덱스 의미가 달라 기존 사용자 목록 양식을 잘못 재해석하지 않도록 request-list-v1 별도 양식 컨텍스트를 사용하며 이전 양식 설정은 보존한다. 브라우저 자료와 D1 자료는 여전히 별도다.
