# 발주서 일반 현황 집계 0.35.0

발주서현황의 집계에서 자체 발주 입력 자료를 최대5축으로 조회합니다. 일반 현황 E040306과 미입고/잔량 E040307의 의미를 구분합니다. 자체 수량은 입력 수량이며 입고된 구매 수량을 차감하지 않습니다.

## 사용 예와 합격 조건

품목명[규격]/거래처를 선택하면6열, 첫 축 소계와 합계가 나와야 합니다. 단일 축은5열/말단 소계 생략, 5축은9열/비말단 축4개 소계입니다. 첫 축 소계를 꺼도 하위 소계는 상위 코드 경계를 가로지르지 않아야 합니다. 칸은2개에서 선택 수+2개로5개까지 늘고 지워도 줄지 않습니다. 초기화는 내역/빈2칸/기본 소계로 돌아갑니다. 조회 오류/미검색 조건은 마지막 성공 출력에 섞이지 않아야 합니다. CSV와 인쇄는 같은 결과를 사용하고 읽기 전용 조회는 저장 자료를 바꾸지 않아야 합니다.

## 원본 관찰과 실제 REA

원본 일반 발주서현황의 후보 목록/1·2·5축 검색을 직접 관찰했습니다. 5축 헤더는 품목명[규격]/거래처/담당자/창고/월별/수량/공급가액/부가세/합계입니다. 마지막 축 소계가 없고 비말단 소계는 안쪽부터 바깥쪽, 전체 축5칸 병합, 직전 해당 표시값+' 계'였습니다. 첫 축 OFF에서 하위 표시값이 같은 상위 경계를 만났지만 하위 소계가 경계를 넘어 합쳐지지 않았습니다. 표시값 구조의 근거이며 raw SID/서버 GROUPBY를 입증하지 않습니다. 첫 소계ON을 복원하고 내역/F8로 돌아갔습니다. 복원된 내역은 동적10열로 기존 자체 그룹형 상세와 동일하다고 기록하지 않았습니다.

정확히 DOM에서 관찰한 공개 JS2본문을 일반 비인증GET 각1회로 확보하고 실제 REA6.4.0으로30초/2GiB 한도 분석했습니다. ESG016R은12,750B/오류0/완료28callable·50call·53frontier, grid는1,638,337B/구문 오류5/복구AST 부분3121·18299·25130입니다. grid 분석을 전체 완료로 올리지 않았습니다. 누계84본문25,247,564B, static완료82/부분2, semantic완료77/부분2/timeout3/OOM2입니다. 과거82본문과 실패 상태를 보존했습니다.

ESG016R의 메뉴515·구매발주 설정·FromProgramIdE040306을 확인했습니다. 집계 설정과 그리드/그래프 전송 분기는 존재하지만 서버가 수량/금액/출력 양식을 반환합니다. 전표 링크는 입력 수정창E040301을 열어 summaryLink와 다릅니다. 원본 API/저장/설정 적용/주입력행 조작/출력은 실행하지 않았고 회사 자료/세션URL은 보관하지 않았습니다. 공개 원문은 실행 자원에 넣거나 실행하지 않았습니다.

## 자체 정책과 검증

17개 비식별 축, raw코드 그룹/자체 코드순·방향, 현재 명칭[규격]/명칭, 자체 날짜 버킷·현재 마스터 그룹을 사용합니다. 계획/발주서는 전체 prefix 경계/말단 생략/합계, 구매는 기존 활성축 경계/말단 소계/총합계로 구분합니다. 기존 날짜·납기·품목·거래처·창고·프로젝트·통화·검색 조건과 혼합통화 거부를 유지합니다. 부분/전체 입고 뒤에도 일반 발주 입력량 집계가 유지되는 합성 회귀 검사를 추가했습니다.

새9개 핵심/UI와2개 실제 모듈 경로 검사를 추가했습니다. 통합 검사에서 일반 보고서 인쇄창이 메뉴 이동 후 남는 결함을 발견해 반환된 인쇄창을 추적하고 destroy시 정리하도록 고쳤습니다. 구매 상세 전용 helper는 발주서에 연결하지 않았습니다. 검사 수/해시는 order-aggregate/validation.json에 기록합니다. DB/저장 자료 구조는 바꾸지 않았습니다.

코드명순은 원본 선택 전환만 관찰됐고 실제 필드 인코딩·동일 명칭·빈값·한글 비교·서버 정렬 소비자가 확인되지 않아 구현하지 않았습니다. 집계대상/출력 양식·주차/거래유형/관리항목·그래프/비교/결재/상세·원본 수량/세금/환율/출력 규칙과 로그인된 호스팅 업무 검증도 남아 있습니다.
