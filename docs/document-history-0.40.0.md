# 구매 전표 이력조회 0.40.0

발주요청·발주서·구매 조회에서 선택 전표 없이 이력조회를 엽니다. 원본 요청 메뉴505는 IHistoryListPage의10열, 발주서509·구매511은 ES303M의11열로 직접 대조했습니다. 작업일자·전표일자·거래처·품목·창고·프로젝트·담당자·자체 행위·검색어로 조회하고 마지막 성공 결과를 CSV로 내보냅니다. 요청은 보관된 전체 기록을 조회하며, 발주서·구매는 기본으로 전표별 마지막 기록을 먼저 고른 뒤 조건을 적용합니다. 이 적용 순서는 자체 정책이며 원본 서버와 동등하다는 뜻이 아닙니다.

## 보관·이전 백업

기존 v2 업무 자료에 선택 항목 documentHistory v1을 추가합니다. 과거 로그를 해석하거나 현재 전표를 과거 이력으로 생성하지 않습니다. C.command의 전체 검증이 성공한 뒤 실제로 변경된 요청·계획·발주서·구매 전표만 기록합니다. 신규·수정·상태변경을 구분하고 자동 연결 진행 변경도 포착합니다. 반복 무변경 저장·조회·실패는 기록을 추가하지 않습니다. 발주계획은 기록만 준비하며 목록 진입 버튼은 아직 연결하지 않습니다.

최근200개 이벤트를 독립 순번으로 보관해 기존 전표 번호·일반 로그 순번을 바꾸지 않습니다. 시작 시각·작업일자·전표 종류/ID/일자·당시 첫 거래처/품목 요약과 전체 식별 코드·담당자·창고/프로젝트·상태·변경 필드명만 기록합니다. 요청/계획의 행별 공급처도 모두 정확한 코드로 검색합니다. 표시명은200자로 줄일 수 있지만 식별 코드는 자르지 않습니다. 본문/행의 변경 전후 사본은 보관하지 않습니다.200건은 이벤트 개수 제한이며 바이트 크기 제한이 아닙니다. 기존 브라우저 저장 용량 오류는 저장 성공으로 처리하지 않고 이전 자료를 유지합니다.

documentHistory가 없는 기존 백업은 추가·추정 없이 복원합니다. 항목이 있으면 v1의 루트/이벤트 허용 키, 독립 순번/중복·순서, 날짜·행위·종류, 코드/배열/표시 자료를 검증합니다. before/after 등 알 수 없는 본문 필드는 거절합니다. 기존에 허용되던 긴 코드·501행 이상 전표도 상태변경을 막지 않고 실제 코드/행수를 보존합니다. 현재 신규 입력의500행 제한은 유지합니다. 새 이력은 현재 기준 자료와 독립된 당시 메타데이터이며 현재 이름 변경으로 과거 표시명을 바꾸지 않습니다.

동일 코어를 사용하는 D1 업무 API에서도 이후 변경 메타데이터를 보관할 수 있지만, 이번 이력 화면은 현재 계정의 브라우저 업무 자료를 조회합니다. D1 API 영역·API 처리 로그와 합치지 않습니다. 새 D1 테이블이나 SQL 마이그레이션은 없습니다. 선택 백업 항목이 늘었으므로 저장 형식이 전혀 바뀌지 않았다고 기록하지 않습니다.

## 원본·실제 REA 근거

원본 발주서·구매 이력은 작업일자/전표번호/행위/거래처코드/거래처명/품목명/담당자코드/담당자명/작업자/전표상태/이력11열입니다. 요청은 일자-No./품목명(요약)을 쓰고 거래처코드 열이 없는10열입니다. 요청 검색창의 표시 체크박스는 수정일자순(정렬) 하나이며 최종이력 항목은 관찰되지 않았습니다. 이 사실만으로 원본 백엔드 전체/최신 범위를 단정하지 않습니다. 자체 요청은 전체 보관 이벤트를 조회합니다.

ES303M에서 최종이력만 검색은 체크, 수정순·시간사용은 해제 상태였습니다. 별도 행위 선택창17개 표시명은 ACTION 코드와 구분합니다. 원본에서는 검색 조건·행위 선택창 열기/닫기만 수행했고 업무저장·삭제·발송·설정저장·Excel/다운로드·주 입력행·날짜/H 링크·비공개API는 실행하지 않았습니다. 세 이력창을 닫고 부모 목록 복귀를 확인했으며 회사 업무값·로그인/세션 자료는 보관하지 않았습니다.

DOM에서 관찰한 공개 ES303M 스크립트 URL을 일반 비인증 GET1회로 받아 실행하지 않고 실제 REA6.4.0의 정적/의미 분석을 수행했습니다.32,475B·SHA b52d0a6505b4309408bc699c37bd2207d6b85e7c80186b2f727ada5652c529b9, parse0·callable153/call299/frontier316·415ms, 예산30초/2GiB이며 두 분석 모두 완료했습니다. 누계85본문25,280,039B, 정적83완전/2부분·의미78완전/2부분/3시간중단/2메모리중단입니다. 기존84 기준과 오류/중단을 보존했습니다. 원문/IR은 실행 자원이나 소스 저장소에 넣지 않았습니다.

계약은 evidence/global-rea-20261018/document-history/에 있습니다. ES303M 조회/Excel 경로, 3개월 제한 선언, ETC_CHK/SORT_MODIFIED_DT 전달, 날짜 링크와 H 상세 링크의 차이를 실제 근거로 확인했습니다. 날짜 링크는 수정 모드 전표로 연결될 수 있으므로 조회 전용이라고 간주하지 않습니다. H의 ES303P 구현과 권한·서버 이력 버전/보관·정렬/최신 적용 순서·정확한 날짜 경계·출력은 미확인입니다. 요청 IHistoryListPage의 구체 구현도 보존 소스에 없어 ES303M payload를 재사용하지 않습니다.

## 합격 조건과 한계

신규15개 검사는 이전 백업의 이력 미생성, 번호 독립, 저장 실패/조회 무변경, 신규·수정·상태·연결 진행,200건 제한, 엄격한 백업 구조, 긴 식별 코드,501행/501품목, 행별 거래처, 작업/전표 날짜 분리, 선택 없는 읽기 전용 진입, 요청10/발주서·구매11열, 성공/대기 CSV 분리, 잘못된 기간, F3/F8/Escape·닫기/이동 정리를 검증합니다. 초기 잘못된 샘플 가정과 전역 버튼을 누르던 테스트는 명시적 이전 백업과 모달 내부 버튼을 쓰도록 고쳤습니다. 독립 검토의 네 결함을 수정하고 재검토에서 추가 확정 결함은 없었습니다. 최종 검사 수·로그 해시는 document-history/validation.json에 기록합니다.

작업자는 미기록, H 상세는 미지원으로 표시하며 전표 날짜를 입력/수정 창에 연결하지 않습니다. 출력·발송·삭제/복구·결재 기록은 임의 생성하지 않습니다. 자체 기록은 브라우저 백업으로 편집 가능한 메타데이터이며 원본 서버의 감사 이력과 동등하지 않습니다. CSV는 자체 성공 목록으로 원본 Excel 형식/권한과 같다고 주장하지 않습니다. 호스팅 앱 로그인 후 업무 검증과 전역 버튼 동등성은 남아 있습니다.
