# 발주요청 일반 현황 집계 0.36.0

발주요청현황에 자체 요청 자료의19축/최대5축 집계를 연결합니다. 요청은 조건5칸을 처음부터 표시하고 말단을 포함한 소계와 총합계를 사용합니다. 기존 계획/발주서의 말단 생략/합계와 구분합니다.

## 사용 예와 합격 조건

품목별/거래처별을 선택하면6열, 거래처 소계→품목 소계→총합계가 나와야 합니다. 수량 열은 수량 (낱개 단위)입니다. 첫 축 소계를 꺼도 하위 소계는 상위 그룹을 가로지르지 않아야 합니다. 초기화는 현황/빈5칸/기본 소계로 돌아가고 이전 스냅샷에 소계가 없으면OFF를 유지합니다. 미검색 조건/조회 오류가 성공 출력에 섞이지 않아야 합니다. 원본 전표가 아닌 가상 자료로 부분 계획 생성 후에도 요청 입력량 유지, 읽기 전용 CSV/인쇄, 저장 무변경을 검증합니다.

## 원본과 실제 REA

원본 메뉴514의 실제DOM 프로그램E040318을 확인했습니다. 보관 purchase_request_page_meta의 B_000000E040314/M_000000E040318/발주요청현황과 맞습니다. E040305는 구매현황 메뉴SID로 요청 식별자에 사용하지 않았습니다. 보관84본문에서21정확참조/9원문callable/5기존 excerpt 참조를 연결했습니다. 허용축·열·요청별 필터/계산식은 동적 template와 서버에서 옵니다. common 전체OOM·Flexion timeout·grid5구문오류 부분 분석을 보존하며 신규GET/의미분석 재시도/원문 실행은 없습니다.

현황/집계·처음부터5칸·후보 목록과1/2/5축 결과를 직접 확인했습니다. 1축은5열과 말단 소계·총합계, 2축은6열과 말단→상위 소계/전체2축 병합입니다. 5축은9열/전체5축 병합/말단→상위 소계입니다. 첫 축OFF에서 나머지 표시값이 같은 상위 경계도 하위 소계를 나눴습니다. 이 근거로 자체 요청 소계는 전체prefix를 유지합니다. 원본 rawSID/서버 GROUPBY 전체를 입증하는 관찰은 아닙니다.

중요한 차이도 남겼습니다. 조건칸은 품목/거래처/담당자/창고/월별 순서였으나, 나중에 세 번째 담당자를 선택한 뒤 결과는 품목/거래처/창고/월별/담당자 순서였습니다. 동적 출력양식/생성순서 규칙은 미확인입니다. 날짜 소계 제목도 구두점 정규화 후에만 대응했습니다. 보충23참조에서 standard placeholder가 없으면 기존 template열을 유지하는 분기와 별도 날짜 소계 formatter를 확인했지만 현재 요청 화면의 분기/내부키와 연결하지 못했습니다. 자체는 선택칸 순서와 자체 날짜 포맷을 사용하며 원본 출력 순서/포맷 전체 동등성으로 기록하지 않습니다. 첫 소계ON과 현황 모드를 복원했습니다. 회사 자료/세션 URL을 보관하지 않았고 원본 저장/설정 적용/주입력행/출력/비공개API를 실행하지 않았습니다.

## 자체 정책과 검증

19축은 기존 자체 코드/마스터/날짜/그룹 및 REA 전표·현재 행 식별자를 사용합니다. 주차·거래유형·관리항목은 계속 미지원입니다. 원본 원시SID·전표/행 표시 의미와 동일하다고 주장하지 않습니다. 수량/공급가액/세금은 입력 요청 행의 effectiveLineTotals이며 계획으로 처리한 수량을 차감하지 않습니다. 원본 전체요청량/잔량/반올림/환율/상태 공식을 확인했다는 뜻이 아닙니다. 행 거래처와 기존 번호/기간/납기/품목/창고/프로젝트/통화/검색 조건, 혼합통화 거부를 유지합니다.

요청 소계는 prefix+말단 포함+총합계, 계획/발주서는 prefix+말단 생략+합계, 구매는 기존 활성축 비교+말단 포함+총합계로 구분합니다. 새8개 핵심/UI와2개 실제 모듈 통합 검사를 추가했습니다. 구매 전용 상세 helper/그래프/비교/명시 정렬을 요청에 연결하지 않았습니다. DB/저장 자료 구조는 바꾸지 않았습니다. 검사 수/해시는 request-aggregate/validation.json에 기록합니다.

동적 양식/집계대상/열순서·주차/거래유형/관리항목·요청 상세/그래프/기간비교/결재·서버 수량/세금/출력 규칙·호스팅 로그인 업무 검증과 전역 상세 재현은 남아 있습니다.
