# 거래유형·관리항목 원본 대조와 후속 개발

## 현재 상태

운영0.49.0, 기능1893acd/최종 확인35877e8, 시작 시 main/origin main 동일·작업트리 정상이다. 사용자가 거래유형·관리항목부터 원본 대조·개발·기존 자료/양식 보존·운영 반영까지 요청했다. 기존 WSL/Supabase/Cloudflare 구성을 유지한다.

사용자 원본 재로그인 후 거래유형·관리항목 분리 팝업을 재관찰했다. 0.50.0 구현과 전체 verify:local(합성 브라우저27개·릴리스4개 포함), 새 Node12개·브라우저2개, 자체3파일 REA 파싱/근거 검증(전체 UI 의미그래프 일부 생략을 명시하고 변경10범위로 보완)이 통과했다. 기존 자료와 비공개 설정·서버 상태·메일을 새 비공개 백업했다. b7726ee 업로드 후 기존 WSL 서버(PID670106)에0.50.0을 반영했다. 공개 버전/코드 해시·Supabase 백엔드·익명 API 차단과 배포 직후 서버 상태21/0·메일·비공개설정 동일을 확인했다. 운영 브라우저는 새로고침 후 세션 만료로 재로그인을 요청했으며 인증 UI/브라우저 전후 비교는 대기 중이다. 아래 확정 범위와 제한을 따른다.

## 기존 구현의 확인된 차이

- `dist/inventory-ui.js` 구매4업무의 transactionType은 읽기 전용 문자열이며 원본 세무 규칙 미검증으로 표시한다. 별도 vatRate(로컬 계산)와 연결되지 않는다. 기존 단일값/양식ID·기존 금액을 보존해야 한다.
- 구매 조회에는 원본에서 관찰한 `inv_s$trx_type_purchasesXlist_search_field` 거래유형 조건이 없다. 요청 조회에는 원본에서 관찰한 `inv_m$manage_item_purchase_requestXlist_search_field` 관리항목 조건이 없다.
- 관리항목 기준자료 `masters.controls`와 등록 메뉴는 이미 존재한다. 구매 품목행의 전용 관리항목 컨트롤·명시적인 코드 검증/검색·코드 변경 참조 갱신은 없다. 기존 코드 `saveDoc`/`lineTotals`가 임의 행 메타데이터를 보존하므로 도입 시 예전 필드·백업을 무조건 정규화하지 않는다.

## 원본 공개 코드 근거

원본에서 관찰해 보관한 공개 `inventory.75a19601.js`를 인증정보 없이 다시 읽어 원래 SHA-256과 일치함을 확인했다. 원문은 실행하지 않았다. `ChangeVatRateSvc`, `GetVatRateByPrioritySvc`, 관리항목 입력 가능 여부를 확인하는 두 메서드를 정확한 AST 범위·원본 해시와 연결해 분리했다. 고정 REA6.4.0으로4범위 파싱 실패0·근거 스키마/입력/결과 해시를 검증했다. 의미 범위는 unknown, 생략 없음이며 외부 바인딩·실제 메뉴 연결/서버 동작은 미확인이다. 전체 의미 분석이나 기능 동등성 완료가 아니다.

해당 코드에는 거래유형의 직접 설정 부가세율이 품목/창고/기본 설정보다 우선하고 변경 시 재계산하는 분기가 있다. 관리항목은 detail의 manage_item/manage_item_cd이며 품목·환경 설정에서 사용 안 함이면 선택값을 지우는 분기가 있다. 이는 공개 코드의 분기이며 현재 회사의 세율표/기본값·허용 항목을 판정하지 않는다. 선택 코드만 보고 세율을 추정하면 안 된다.

원문·범위 manifest·결과: `.artifacts/purchasing-transaction-management-20261020/`. 기존86누계와 운영 근거는 바꾸지 않았다.

## 구현·보존·배포 기준

관찰된 조건부터 기존 명시 F8/성공·대기 분리와 다중 피커를 재사용한다. 거래유형은 기존 transactionType 값을 보존하는 코드/표시 정책, 관리항목은 기존 등록자료를 참조하는 선택적 행 코드로 설계하되 실제 저장 이름·범위는 팝업/공개 코드 대조 후 확정한다. 등록만 있는 관리항목을 새 등록 기능으로 다시 만들지 않는다.

기존 v2 백업·기본 금액·커스텀 양식의 안정ID/숨김/기본값·원본 충돌·미저장 변경을 보존한다. 관리항목 코드 변경/사용중단과 과거 참조도 검사한다. 세율은 명시 근거와 사용자의 실제 선택 없이 기존 전표에 일괄 적용하지 않는다. 새 전표/명시 변경·무변경·실패·전표 연결과 검색/CSV를 합성 검사한다.

관련 Node/jsdom·localhost 브라우저 및 전체 verify:local·릴리스·범위별 REA검증 후 버전·커밋/푸시한다. 배포 전 브라우저 전표/양식·서버 상태·메일·비공개설정을 새로 비공개 백업하고 기존 관리 서버만 수동 재시작한다. 새 운영 로그인/해당 조회·팝업을 읽기 전용으로 확인하고 브라우저 백업 파일·보호 계정/설정·메일을 전후 비교한다. 원본/운영 업무자료 저장·메일 발송은 하지 않는다.

## 원본 재로그인 후 확정 · 구현0.50.0

사용자 재로그인 후 구매 거래유형 팝업의 코드21/22(부가세율 적용/미적용), 두 체크박스·검색/적용/닫기와 요청 관리항목 코드/명·복수 선택/사용중단 포함/닫기를 직접 확인했다. 회사 관리항목 목록은 수집하지 않았다. 두 분리 팝업의 정확한 공개 스크립트 URL을 확인했다. 원본 입력행/저장/설정 저장은 조작하지 않았다.

구매 조회에 거래유형, 요청 조회에 관리항목 다중 검색을 추가한다. 입력의 거래유형 안정ID는 유지하고21/22를 명시 선택할 수 있게 한다. 자체 정책은22로 명시 변경/신규 선택 시 로컬 세율0,21은 사용자가 확인한 로컬 적용 세율이다. 기존 코드/미기록·기존22 전표도 로드/백업/무변경 저장 시 기존율/금액을 보존한다. 원본의 품목·창고별 세율/직접설정·회사 기본율 전체 동등성은 아직 미확인이고 자동 추정하지 않는다.

관리항목은 기존 masters.controls를 참조하는 선택적 managementItem 품목행 코드다. 기존 양식을 바꾸지 않도록 기본은 숨김이며 Option 품목BODY에서 표시해 입력한다. 검색은 복수 OR/관리항목이 있는 품목행 일치이며 요청 전표는 중복 없이 한 번만 표시한다. 예전 코드/사용중단·백업·코드 변경 참조/수정 초안을 보존한다. 관찰되지 않은 다른 조회의 새 검색 항목은 추가하지 않는다.
