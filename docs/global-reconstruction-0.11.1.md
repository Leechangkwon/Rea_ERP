## 실제 REA 실행

원본 공개 JS 49개, 7,816,239B를 SHA256으로 구분하고 `rea-agents` 6.4.0 라이브러리의 정적·의미 분석을 실제 실행했다. 기존 41개와 현재 화면의 공개 script URL로 추가한 8개를 분리 기록한다. 원본 JS는 실행하지 않았다.

- 정적 파싱: 완전 48개, 오류 복구 부분 결과 1개. upbalance에 StrictOctalLiteral 오류 4개가 있다.
- 의미 분석: 완전 47개, 부분 1개, 시간 초과 중단 1개. 메뉴 bundle은 실제 실행을 시작했으나 제한 시간에 중단해 의미 수량을 unknown으로 남겼다.
- 확인된 수량: AST 607,484개, callable 7,361개, call-site 28,461개, frontier 30,455개. 중단된 메뉴 의미 분석 수량은 합산하지 않았다.
- 버튼·액션 후보 4,082개를 추출했다. 키워드와 AST 기반 후보이며 익명 함수·렌더링·설정·공통 검증도 포함한다. 실제 버튼 개수 또는 전체 버튼 목록이 아니다.

출처·원문 해시·신선도·실패는 `evidence/global-rea-20261018/`에 보존한다. `action-facts.json`은 후보의 심볼·위치·분기/호출/미해결 수량을 저장하며, 실제 관찰은 별도 `ui-observations.json`에 기록한다. 대용량 AST/의미 IR과 원문은 배포하지 않는 `.artifacts/global-rea-20261018/`에 있다. 원본 파일의 URL이 기록되지 않은 purchaseList.js 1개는 출처를 추정하지 않았다. 전체 CLI application graph 성공을 주장하지 않는다.

## 구매 입력의 검증 버튼

원본 E040303의 검증 버튼은 별도 바코드 수량 검증 창을 연다. 빈 스캔 상태의 F8은 필수 입력 오류와 품목 입력 초점을 표시한다. 검증 창의 품목코드·품목명·규격·수량·박스단위 열 및 보조 버튼을 직접 확인하고 닫았다. Option에서 기능설정과 품목범위 창도 열어 확인한 후 저장 없이 닫았다.

0.11.1에서 구매 입력의 기본 검증 버튼은 바코드 대조 창을 연다. 기존 필수 입력 검사는 입력 보조 영역에 유지한다. 원본 `BarcodeVerification`의 `DES_INC`/`SIZE_INC` 조건과 합산 비교를 근거로 자체 저장된 품목범위를 연결했다. 품목코드에 더해 선택한 품목명·규격을 독립 키로 사용하고, 같은 키의 전표 수량과 검증 수량을 각각 합산한다. 코드가 같아도 이름/규격이 다르면 부족과 전표 외 품목으로 구분한다. 명시적 빈 문자열과 마스터 기본값을 구분하며 구분자 충돌이 없는 복합 키를 사용한다.

스캔한 별도 검증 행의 이름·규격·수량을 수정할 수 있다. 검증·다시 작성·닫기·F8은 전표 적용이나 저장을 호출하지 않는다. 현재 전표·사업무 자료·백업 형식은 변경하지 않는다. 원본의 박스단위 환산, 실제 스캐너, 찾기·정렬·My품목의 검증 창 내 모든 하위 기능은 이번 완료 범위가 아니다.

## 재고현황의 복수 정렬

원본 E040701의 정렬/소계/합계 창, 세 초기 순위, 품목명 검색·항목선택 및 선택 후 활성화되는 설정을 직접 확인했다. 변경은 적용하지 않고 닫았다. 공개 FM079P_01·FM083P_02도 실제 REA로 분석했다. 선택 행 순서 이동·삭제·중복 검증·apply/save/close 분기는 정적 근거와 구분해 기록한다.

0.11.1은 3개 정렬 우선순위, 방향, 품목명 기준, 선택 행 올림·내림·삭제, 중복 기준 오류를 제공한다. 적용/F8 때만 자체 조회 조건에 반영하고 닫기는 임시 변경을 버린다. 조회·화면·CSV·인쇄에는 같은 정렬 결과가 전달된다. 기존 단일 `sort` 입력은 유지하고 복수 조건은 `sorts`를 사용한다. 저장 자료 구조와 DB 스키마 변경은 없다.

원본의 모든 정렬 필드, 4개 이상 동적 순위, 페이지 분할·소계 출력·상세 설정·입고단가 합계 계산은 아직 지원하지 않는다. 관련 버튼은 비활성화 상태로 유지한다. 자체 재고 금액 계산을 원본 평가 원가와 같다고 표시하지 않는다.

## 로그인 버전 표시

배포 후 확인에서 로그인 화면의 버전 표기가 과거 값으로 고정되어 있음을 발견했다. 앱 자체 인증과 별개인 표시 문제를 수정했고, 기존 릴리스 검사에 로그인 화면과 패키지 버전 일치 조건을 추가했다.

## 검사와 배포

관련 핵심·UI·실제 Worker 통합 검사에서 품목범위 저장 → 갱신된 앱 설정 → 구매 검증 버튼 → 수량 대조가 연결됨을 확인했다. 원본 설정·회사 자료를 저장·삭제·취소·발송하지 않았다. 전체 `NODE_OPTIONS=--test-isolation=none npm test` 662개와 배포 파일 검사 4개가 통과했다. Worker 1,641,031B·정적 자원 50개를 빌드했다. 실행 로그 해시와 합산 근거는 `evidence/global-rea-20261018/validation.json`에 기록했다.

이 환경에는 연결된 로컬 브라우저 제어 도구가 없어 Sites의 관리형 로컬 미리보기는 시작하지 않았다. jsdom/Worker 통합 검사와 원본 클라우드 화면 관찰을 실제 배포 후 ERP 로그인 업무 검증으로 대신 표시하지 않는다.

배포 대상은 기존 `https://rea.qaredi.com`이며 현재 Sites public audience와 ERP 자체 로그인·권한을 유지한다. 기존 브라우저 업무 자료와 D1 API 업무 자료는 분리한다.

## 버튼별 남은 작업

각 화면·버튼에 원본 관찰, 하위 메뉴/팝업, 입력과 필수 조건, 권한, 실행 결과, 취소/오류, 보관, 실제 REA 위치, 구현, 합성 검사 상태를 각각 기록한다. 상태는 미관찰 → 표시 확인 → 동작 확인 → 구현 → 검증으로 구분한다. 후보 개수나 테스트 통과가 이 단계를 자동 완료시키지 않는다.

구매 우선순위는 발주요청 → 발주계획 → 발주서 → 구매다. 남은 입력 보조·첨부·단위 환산·삭제/복구·이력·저장 분기와 함께, 재고 II·회계 I/II·관리·세무·그룹웨어·데이터센터 487개 경로의 실제 업무 화면을 차례로 관찰하고 구현해야 한다. 원본 저장·발행·송신·삭제의 실행 결과 검증에는 회사 실자료를 변경하지 않는 별도 테스트 환경이 필요하다.
