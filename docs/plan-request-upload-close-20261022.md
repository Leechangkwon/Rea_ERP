## 0.68.0 구현 순서

1. 현황의 request grouped/detail '진행상태' 셀에 현재 전표에만 연결된 상태 버튼을 붙인다. 다른 종류·집계 결과·인쇄/CSV 데이터에는 쓰기 액션을 추가하지 않는다.
2. 기존 transition의 confirmation/progress 명령을 재사용한다. 기본값은 현재 상태, 미확인 전환에서도 기존 progress를 보존한다. 수량/금액/원본/후속전표·양식·메일/재고/채무는 상태 변경의 기존 정책대로 보존하며 새로운 잔량 차단/회계 권한은 도입하지 않는다.
3. 열기 전과 명시 적용 때 계정/회사/role/read/write·현재 report host/query·원문/CAS·선택 전표 snapshot·dialog open/connected를 검사한다. 자료/권한/조회/화면/하위창 교체 뒤 오래된 저장을 거부하고 리스너를 해제한다.
4. 저장 성공 후 성공했던 조회 조건으로 다시 조회하면서 아직 적용하지 않은 날짜/빠른검색·F3 펼침 상태를 보존한다. 취소/읽기 전용은 저장하지 않는다.
5. 합성 현황 완료→reload→목록 확인→현황 재개 및 미확인/확인, 취소·원문변경·계정/권한·지연 callback·후속자료 보존 검사, 독립 리뷰·REA6.4 분석을 거친다. 운영0.67 기반 격리후보 전체 회귀/브라우저 후 commit/push/기존 WSL·Supabase·Cloudflare 배포 및 보존 대조. main VAT5 연구 빌드 금지.

원본은 상태 레이어에서 고르는 반면 자체 앱은 기존 명시 적용 모달을 재사용하는 UI 차이를 남긴다. 원본 서버 저장 결과를 실행하지 않으므로 전체 동등성/실업무 쓰기 합격으로 올리지 않는다. 원본 새 본문은 없고14본문/24요구사항·전체합격0 유지. 모아는 인증 변화 없으면 로컬 pending만 보존한다.

## 구현·집중 검증

현황 상태 버튼과 명시 적용 모달을 연결했다. 취소/재조회/탭 이동/계정·회사·역할·read/write/raw 변경/닫힌 창/저장 용량 오류를 검사했다. 신규Node9, 관련 합계109, 실제 shell 합성 브라우저1개(1280/390px) 통과. 연결된 요청의 미확인 변경은 기존 validateLinks에 따라 거부되고 원문·후속자료가 보존됨을 확인했다. 독립22경계·신규9검사에서 남은P1/P2없음. 운영 저장은 아직 하지 않았고 격리 후보·배포·보존검증이 남아 있다.
