# 구매 조회 검색 적용·목록 보존 · 0.48.0

발주요청·발주계획·발주서·구매를 기존 구현과 재대조했다. 원본 네 조회에서 Search(F3)와 검색(F8), 검색 적용 후 패널 접힘을 실제로 확인했다. 기존 이력·전표별 불러오기·수량/잔량 연결·양식·집계·메일은 다시 만들지 않고 보존한다.

## 사용과 결과

1. 원하는 조회에서 Search(F3)를 열어 조건을 입력한다. 입력 중에는 이전에 적용한 결과·상태탭 건수·선택·CSV를 유지한다.
2. 검색(F8) 또는 빠른검색 Enter로 조건을 적용한다. 성공하면 검색 패널이 접히고 첫 페이지로 이동한다. F3로 다시 열면 조건이 남아 있다.
3. 시작일이 종료일보다 늦으면 오류를 표시하고 이전 결과와 선택을 유지한다. 잘못된 조건을 고쳐 다시 검색한다.
4. 전표 연결·상세 저장·양식 재표시 후에도 적용한 조건과 입력 중인 조건, 상태탭·선택·페이지/스크롤을 나눠 보존한다. 발주서 메일 상태가 나중에 갱신돼도 입력 중인 검색이 실행되지 않는다.
5. 발주계획의 미저장 수량·단가도 목록 재조회 뒤 유지한다. 원본 전표가 달라졌다면 기존 충돌 검사를 유지해 덮어쓰기를 막는다. 한글 조합 중 Enter·수정키/반복 입력은 검색을 실행하지 않는다.

조회 전용 계정은 검색할 수 있고 전표/메일 저장 권한은 늘어나지 않는다. 검색 상태는 화면 메모리에서만 관리하며 저장 모델·DB 스키마·메일 전송 코드는 바꾸지 않는다.

## 원본 근거와 남은 범위

사용자 재로그인 후 Windows 내장 브라우저에서 네 조회의 값 없는 DOM을 확인했다. 원본 회사 입력값·업무행·세션URL·인증정보는 보관하지 않았다. 요청 번호에는 합성 문자열만 입력해 입력 전/후 목록 구조가 유지되는 것과 검색 후 접힘을 확인하고 시험 조건을 지웠다. 원본 주 입력행·행 이동·저장/삭제/발송/설정 저장은 조작하지 않았다.

현재 원본 열 수는 요청11·계획14·발주서12·구매10이고 자체 기본값은11·14·10·12다. 회사별 양식과 버전 차이가 있으므로 원본의 현재 순서를 전역 기본값으로 강제하지 않고 기존 안정 필드ID·사용자 양식·CSV의 의미를 보존했다. 검색 피커의 복수선택/빈값, 발주계획 건별/전표별·수량0 기준, 관리항목·거래유형·수정일자순, 원본 상태/작성자/환산·세무/서버 저장·인쇄·결재 동등성은 미확인이다.

현재 DOM에서 확인한 공개 번들3개(1,101,802B)를 인증 없이 새로 받아 SHA-256과 REA6.4 입력/결과를 검증했다. 구문 분석3개/실패0이며 큰 두 번들의 전체 의미 그래프는 부분 상태다. 검색 액션/브리지 선언을 AST 범위·원본해시로 분리한 두 작은 입력도 분석·검증했다. 외부 바인딩과 현재 버튼의 서버 디스패치 전체를 증명하지 않으며 과거86본문 누계는 그대로다. 자체 수정2파일도 입력·결과 해시/근거 검증과 파싱 실패0을 확인했다. 정적 분석은 원본 전체 동등성의 증거로 확대하지 않는다.

## 검사와 운영

전체 verify:local·관련 Node92개(신규9개 포함)·localhost 합성 브라우저22개(신규2개)·릴리스4개가 통과했다. 원본 구조 비교와 실제 운영 확인은 이 합성 검사와 별도로 기록한다. 기존 계정/서버 상태와 메일3함/8메시지/1파일을 비공개 백업해 무결성·복원미리보기0충돌을 확인했으며 복원은 하지 않았다. 현재 소스 업로드와 기존 수동 서버 반영 전이며 최종 상태는 evidence/purchasing-search-state-20261019.json을 따른다.
