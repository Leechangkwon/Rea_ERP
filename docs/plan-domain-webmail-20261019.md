# REA 자체 도메인 웹메일 · 0.46.0

사용자가 회사 도메인 송수신·REA 메일함·직원별 권한·발주서 연동 추가 개발을 요청했다. 현재 0.45.0 / 6e367a0이며 기존 Gmail 인증·계정·회사·업무자료·Cloudflare Tunnel을 보존한다. 원본 ECOUNT 서버 발송/설정은 실행하지 않는 독립 구현이다.

## 구현

- 상단 메일 진입점과 설정 화면 연결. 받은편지함/보낸편지함/임시보관함/휴지통, 검색·페이지 이동·읽음·회신·명시 저장·최종 확인 발송, 전표 ID 연결과 PDF 첨부. 본문은 텍스트로 표시하고 HTML/외부 이미지를 실행하지 않는다.
- mail.read/mail.write/mail.manage 권한과 메일함 구성원 범위를 매 요청 확인한다. 관리자 권한이 다른 직원의 메일 본문 접근을 자동 허용하지 않으며 메일함 구성원이어야 한다. 메일함 관리/직원 배정은 별도 관리 권한이다. 기존 회사 로그인/CSRF·동일 Origin을 재사용한다.
- 기존 상태 테이블과 별개로 rea_mailboxes, rea_mail_messages, rea_mail_ingress_keys를 추가한다. RLS 활성화 및 anon/authenticated 접근 철회, 서버만 접근한다. 원문·본문·첨부는 소스/로그에 남기지 않는다. 첨부는 private rea-mail-files bucket에 저장하고 ERP가 권한 확인 후 다운로드를 중계한다. SQLite 개발도 같은 기능과 CAS 충돌 규칙을 지원한다.
- 발송 전 메일/권한/메일함 재확인, CAS로 발송 예약 후 SMTP 호출. 같은 요청은 재발송하지 않는다. 수락/실패/불명확을 구분하고 결과 불명확 시 자동 재시도하지 않는다. Gmail 기존 발주서 경로 유지. 새 메일함은 Gmail 발신 주소 또는 검증된 Cloudflare 도메인 SMTP를 사용한다.
- Cloudflare Email Worker → 전용 토큰으로 인증되는 Supabase Edge ingress → 메일함/비공개 첨부 저장. Edge는 MIME 파싱·중복 방지·크기 검증·대상 메일함 확인 후 저장해 로컬 PC가 꺼져 있어도 수신 저장이 가능하도록 한다. Cloudflare에 Supabase 서버 비밀키를 넘기지 않는다.
- Cloudflare 실제 계정 로그인과 현재 플랜 확인은 사용자에게 요청했다. 새 유료 가입/약관 동의 또는 결제는 코드/검증 결과가 준비된 뒤 구체 비용과 변경을 확인한다. 기존 DNS 메일 경로를 덮어쓰지 않고 현황·도메인 인증 상태부터 확인한다.

## 합격 조건

권한/메일함 격리·고객 차단·CSRF/Origin·주소/제목 주입·동시 수정·발송 중복/결과 불명확·첨부 접근·비공개 토큰·MIME 텍스트/HTML/첨부·중복 수신·잘못된 토큰/대상·메일함 비활성·기존 Gmail/전표 보존 검증. localhost 합성 Node/브라우저 → 전체 verify:local·릴리스·REA → 커밋/푸시 → 기존 수동 운영 반영·로그인 후 UI 확인. 실제 외부 송수신과 합성 검증은 구분한다.

## 구현·검사 현황

메일함/메시지 API·화면·도메인 SMTP·비공개 첨부·클라우드 MIME 수신·전표 PDF·직원 권한·백업/무결성/추가 복원을 구현했다. 기존 Gmail 기능을 유지한다. 관련 Node 50개(웹메일 신규 17개 포함)와 합성 브라우저 18개(신규 6개)가 통과했다. 추가한 SQLite 요청 ID 고유 인덱스 문자열 오류를 관련 검사에서 수정했고 최종 verify:local 전체와 릴리스 4개·브라우저 18개를 다시 통과했다. REA 자체 5개 dist/worker 파일에 입력/결과 해시·근거 검증을 적용하며 원본 86개 누계와 동등성 상태는 바꾸지 않는다.

Cloudflare에서 qaredi.com 소유·Workers Free와 월 US$5+사용량 업그레이드 조건을 확인했다. 현재 DNS는 CNAME 5개/TXT 2개이며 MX·SPF·DKIM·DMARC는 없다. 기존 rea Tunnel 레코드는 유지했다. Workers/SMTP 연결과 새 요금제 동의는 소프트웨어·운영 UI가 검토 가능해진 뒤 최종 활성화 단계로 확인한다. Supabase 새 테이블/Edge와 운영 소스 반영은 커밋 업로드 후 진행한다.

## 운영 반영 근거

cae1a31 업로드 후 기존 수동 서버를 0.46.0으로 재시작했다. 기존 로그인 세션·메일함·발주서 자체 메일 연결과 합성 초안 저장을 운영에서 확인했다. 기존 app_state/gateway_state의 내용과 revision 9/0, runtime.env는 전후 동일하다. Gmail SMTP 인증 재검사도 통과했다. 새 Supabase 스키마·비공개 bucket·Edge ingress를 적용했고 합성 MIME/첨부의 실제 클라우드 저장·중복 수신 차단·익명 첨부 차단을 확인했다. 검사 수신은 휴지통·비활성 메일함으로 보존하며 실제 외부 메일은 주고받지 않았다. 백업(3함/1수신/1첨부)과 무결성 검증을 통과했다. 관리자용 서버 전용 RLS 정책 없음 INFO 5개는 의도한 접근 모델이며 보안 경고/오류 및 성능 권고는 0개다.

Cloudflare Paid 전환과 새 전용 수신 연결/발신 토큰의 최종 활성화는 사용자 확인이 필요하다. 기존 CNAME/TXT 및 Tunnel은 변경하지 않았다. 운영 자체 메일함 사용과 Gmail 발신은 연결되어 있지만 회사 도메인 외부 송수신은 아직 활성화되지 않았다.

## 0.46.1 운영 보완

운영 초안 확인 중 작성 화면의 휴지통 이동 버튼 누락을 발견했다. 저장된 초안의 소프트 이동·복원, 신규 미저장 초안에서는 버튼 숨김, 저장 중 메일함 변경 차단을 보완했다. 새 회귀 흐름을 포함한 브라우저 19개와 최종 verify:local 전체가 통과했다. 소스 7e0bf0d 업로드 뒤 기존 수동 서버에 반영했다. 사용자에게 월 US$5+사용량 및 연결 키 등록 승인을 받았고 Cloudflare 결제 마지막 단계의 약관/자동청구와 Wrangler 배포 연결 확인을 요청했다. 실제 구독·메일 DNS/외부 송수신 활성화는 아직 하지 않았다.

## 0.46.2 최종 활성화

사용자가 Workers Paid 월 US$5+사용량과 약관/자동 청구, Wrangler 연결을 승인했다. 구매 완료 화면을 확인하고 제한한 OAuth 스코프(account/user 조회, Worker scripts 편집, zone 조회, 이메일 발신/라우팅 편집)로 연결했다. 수신 Worker/전용 키를 배포하고 qaredi.com 발신·수신 온보딩 DNS와 purchase@qaredi.com 수신 규칙을 적용했다. 기존 다섯 웹사이트 Tunnel/CNAME과 두 확인 TXT를 보존했다. 전체 DNS 18개(CNAME5/MX6/TXT7), 루트/반송 MX·SPF·DMARC 해석, 라우팅 enabled와 purchase 단일 규칙/기본 전체수신 비활성을 확인했다.

사용자가 생성한 발신 토큰은 화면 표시값을 출력하지 않고 600 임시 파일로 전달해 SMTP 인증 후 runtime.env에 원자적으로 저장했고 임시 파일은 제거했다. 기존 모든 설정값은 동일하며 도메인/발신 토큰 두 키만 추가했다. 원래 도메인 입력에 qaredi가 들어가 생긴 설정 오류를 재현해 --domain 고정 입력과 사전 도메인 검증으로 보완했다. 웹메일 Node18개/관련51개·브라우저19개와 최종 verify:local 전체를 통과했다. 소스 2148428을 업로드 후 기존 수동 서버에 0.46.2를 반영했다. 원격 수신 경로·SMTP 인증은 연결됐고 실제 외부 메일 발송은 아직 없다. 운영 UI가 로그인 화면으로 돌아와 기존 계정 재로그인, 최종 두 방향 시험 메일 각1통의 명시적 발송 확인을 요청했다.

## 0.46.3 실제 송수신 검증 중 수신 보완

기존 계정으로 0.46.2 로그인 후 REA purchase@qaredi.com → Gmail 시험 1통의 실제 INBOX 도착을 확인했다. 승인된 반대 방향 1통은 Gmail 접수/SENT 후 Cloudflare Email Worker 예외로 일시 실패했다. Supabase에는 호출되지 않았다. Workers는 redirect:error를 지원하지 않아 요청 생성 시 예외가 발생한다. 설치된 Wrangler 4.151.1의 Miniflare/workerd에서 원래 옵션의 동일 예외와 manual 변경 후 성공을 재현했다. manual은 리디렉션을 따라가지 않으며 비정상 상태를 실패로 처리해 전용 키 전파를 막는다. MIME 스트림·리디렉션/일시 오류·크기/대상/설정 검증의 회귀 검사를 추가했다. 원래 외부 시험 메일은 추가 발송하지 않고 제공자 재시도를 기다린다.

소스 5780f5f 업로드 후 Worker c1f54ff0-bdfe-48f1-90bc-7259fba13385를 100% 배포하고 기존 WSL 서버를 0.46.3으로 수동 재시작했다. 기존 로그인 유지·메일함 진입·공개 로그인200/익명 메일401/내부 health404를 확인했다. Gmail 실제 수신 헤더 SPF/DKIM/DMARC 모두 pass다. 실제 workerd에서 기존 전용 키로 Supabase에 연결해 미등록 대상404를 받았으며 SMTP 발송/메일 저장은 없는 검사다. 보호 대상 계정·비밀번호·회사·설정·권한·업무자료와 기존 비공개 설정값은 동일하다. app revision9→11은 lastLoginAt/세션/시도/감사/로그인 기록만 변경됐고 gateway revision0은 완전히 같다. 비공개 백업3함/3메시지/1파일의 무결성 및 추가 복원 미리보기0충돌을 확인했다. 관리 페이지68에 현재 도착/미도착 구분과 남은 수신 확인을 기록하고 이전 이력을 보존해 재조회 검증했다.

원래 수신 시험은 09:54:29Z·09:59:47Z 수정 전 두 번 일시 실패했다. 10:07:40Z에 수정 배포했고 10:15Z 저장소 재조회에서는 아직 도착하지 않았다. Google 자동 재시도 시각은 제어하지 않는다. 사용자가 정한 각 방향1통 제한을 지켜 외부 추가 발송은 하지 않았고, 즉시 최종 검증을 위한 추가1통의 선택 확인을 요청했다. 승인 또는 원래 메일 도착 후 실제 운영 받은편지함과 메시지 ID/첨부 없음·원문 중복 여부를 확인할 것.

## 실제 양방향 검증 완료 · 2026-10-19

사용자가 추가 시험1통 발송을 명시 승인했다. 기존 Gmail SMTP로 연결 안내만 포함한 추가1통을 전송했고 Gmail SENT와 실제 Supabase 받은편지함 저장을 확인했다(19:23:23 KST). 운영0.46.3 기존 로그인 세션에서 구매팀 메일함·받은편지함·본문·첨부 없음·읽음 상태 저장을 확인했다. 해당 Message-ID 레코드는1건이다. 그동안 원래 시험도 Google 자동 재시도로19:24:37 KST에 수신됐다. 총 외부 전송은 회사→Gmail1통과 Gmail→회사2통이며 그 이상의 추가 발송은 없다. 회사 발신의 Gmail 실제 INBOX 및 SPF/DKIM/DMARC pass와 함께 양방향 검증을 완료했다. 실제 수신 근거는 .artifacts/domain-mail-20261019/real-gmail-to-rea-recheck-1.json 및 original-gmail-final-receipt.json, 화면은 Windows browser-handoff/domain-mail-real-received-0.46.3.png다.

최종 비공개 메일 백업3함/5메시지/1파일의 무결성과 복원 미리보기0충돌을 확인했고 복원은 실행하지 않았다. 보호 대상 계정·비밀번호·회사·역할·설정·업무자료와 기존 runtime 값 보존을 다시 확인했다(app revision11, gateway0). 관리 페이지69에 실제 양방향 완료와 최초 실패/수정/최종 수신을 구분해 기록했고 모든 변경/이전 이력을 재조회 검증했다. 코드 변경은 없으므로0.46.3과 기존 전체 검사 결과를 유지한다. 원본 ECOUNT 웹메일 전체 동등성은 여전히 선언하지 않는다.
