# 전표 진행상태 사용과 검증 0.7.1

발주요청·발주계획·발주서 등 전표 조회에서 전체, 미확인, 확인, 진행중, 완료별 건수를 확인하고 필터링한다. 상태 칸을 누르면 해당 전표만 변경한다. 여러 전표는 체크 후 `진행상태 변경`에서 대상·현재 상태를 검토하고 `상태 변경 적용`을 누른다. 현재 검색/상태 필터로 숨겨진 전표는 선택이 남아 있어도 일괄 변경하지 않는다. 새 입력과 수정 창에도 진행상태를 표시한다.

## 상태와 수량

- 미확인: 목록에 남아 있지만 재고·채권채무·후속 전표 잔량에 반영하지 않는다. 원본으로 후속 전표를 생성할 수 없다.
- 확인: 확인한 전표로 업무 계산에 반영한다.
- 진행중: 처리 중인 전표다. 기존 저장값 `진행`을 유지하며 화면에만 진행중으로 표시한다. 입력값 진행중도 진행으로 정규화한다.
- 완료: 완료 표시이며 전표·입고·판매를 자동 생성하지 않는다. 기존 활성 전표의 재고·금액 반영도 유지한다.

신규 기본값은 기존 진행 상태를 유지한다. 신규/수정 시 자동 미확인으로 전환하는 회사·사용자별 정책이나 별도 확인권자 권한 설정은 이번에 추가하지 않았다. 현재 변경은 기존 inventory.write 권한을 따른다. 외부 그룹웨어 전자결재나 신원 기반 다중 승인과는 별도다.

발주계획의 수량 기준 조회는 `발주 잔량`으로 별도 제공한다. 저장된 진행상태와 잔량 유무를 같은 상태로 간주하지 않는다. 완료 표시를 바꾸는 것만으로 남은 수량을 없애거나 사용 수량을 변경하지 않는다.

## 보호와 호환

기존 inventory v2 저장 형식을 유지한다. 미확인 상태의 v2 백업을 복원할 수 있고 기존 진행/완료 전표는 그대로 읽는다. 잘못된 상태값과 미확인·취소 전표의 회계반영 위조는 거부한다. 일괄 변경은 복사본에서 원자 처리한다. 연결된 후속 전표, 사용한 재고, 지급 기록, 회계반영, 구매실 월마감의 기존 검증을 거치므로 상태 변경으로 이 보호를 우회할 수 없다. 변경 전후 상태는 재고 업무 로그에 남긴다.

브라우저 업무자료와 서버 D1 업무자료는 계속 별도다. 이 화면의 진행상태 변경을 D1 전체 업무자료 동기화나 신규 HTTP 상태변경 API로 표시하지 않는다. 기존 HTTP 신규전표 입력은 기존 진행 기본값을 유지한다.

## 원본 근거와 한계

- 이카운트 공식 중급 유통 교재 실제 PDF 16–17쪽: https://download.ecounterp.com/doc_Ecount_distribution.pdf?ver=2026030501 . 미확인 상태는 재고·매입·매출에 영향이 없으며 조회의 미확인 탭에서 전표를 선택하고 진행상태변경→확인으로 처리한다. 신규 확인/미확인, 수정 유지/미확인 및 확인권자 유형 설정도 설명하지만 이 설정 전체를 이번 구현과 동일하다고 주장하지 않는다.
- 기존 공개 JS REA 근거 `evidence/purchase-manual-rea.json`의 REA-MAN-02: finish_step_button_tf/complete_tf의 complete 또는 in_progress 분기, PROC_NO·PROC_STEP·PROGRESS 전달, from_progress_status 데이터 결합. 회사별 기본 설정·서버 성공·전체 상태전이 규칙을 입증하지 않는다.
- 추가 분석은 수정한 자체 배포 코드의 상태 관련 함수만 REA 6.4.0 원본 라이브러리로 정적 분석한다. 대상 코드를 실행하지 않고 CLI application graph 성공으로 표시하지 않는다. 입력·결과 hash와 범위는 `evidence/document-status-0.7.1.json`에 기록한다.

관련 검사: `tests/document-status.cjs`, `tests/document-status-ui.cjs`. UI는 jsdom 합성자료 검사이며 실휴대폰·호스팅 업무 화면의 실제 관찰과 구분한다.
