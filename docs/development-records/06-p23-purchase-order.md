# P2.3 — 발주서·거래처·출력·메일

## 당초 계획

계획/단가 확정에서 발주서를 만들고 거래처별 추적, 양식·Email, 진행상태, 부분 구매와 잔량을 확인한다. 발주서 생성 성공과 외부 발송 결과는 구분한다.

## 기존 → 변경과 이유

- 매번 상단 거래처를 수동 지정 → 품목행 명시 구매처→구매계열 저장 머리→품목 기본 구매처 순서를 공통 적용했다(0.62). **왜:** 사용자 테스트에서 품목에 등록한 구매처가 발주 생성까지 이어지지 않아 다시 선택해야 했기 때문이다. 과거 구매처 공란을 아무 거래처로 채우지 않는다.
- 새 발주서에 고객 C001 자동 선택 → 0.88.5 새 발주서는 빈 거래처로 시작한다(`6aac054`). **왜 재수정했는가:** `purchaseorder`가 영업용 `order` 정규식에 포함돼 고객 기본값을 상속하고, 요청/확정 구매처의 자동 반영을 막는 원인을 확인했기 때문이다. 기존 저장 전표와 명시한 초안 거래처는 유지한다.
- 단가 확정/연결 출처와 불일치하는 발주 → 원본행/확정 단가·거래처를 보존하며 부분 구매까지 연결했다. **왜:** 현재 품목 기본값이나 수동 우회가 확정 비교 결과를 덮지 않아야 하기 때문이다.
- 별도 기능처럼 보이는 Option → 0.88 기존 계획→발주 진행규칙 편집기를 재사용했다(`e665dc1`). **왜:** 같은 설정의 두 저장소와 서로 다른 동작을 새로 만들지 않고 기존 연결 규칙을 일관되게 적용하기 위해서다.
- 출력/메일 버튼만 존재 → 0.45 발주서 Gmail 작성/PDF·영속 발송 결과, 이후 자체 웹메일을 연결했다. **왜:** 미리보기·메일 작성창·실제 발송/수신을 분리하여 결과를 확인해야 하기 때문이다. 메일 운영의 자세한 경위는 P8 기록을 따른다.

## 검증과 한계

품목→요청→계획→발주 자동 구매처, 직접 불러오기, 명시 거래처 보존·복수/미지정 거절, 확정 구매처 V002의 부분 처리와 잔량은 합성 저장/재조회 근거가 있다. 운영에서는 기존 자료를 보존한 모달 열기/취소 등을 수행했다. 과거 별도 승인된 메일 송수신 이력과 이번 작업을 혼동하지 않는다. 이번 문서 작업의 업무 저장·메일 발송은 없다.

## 앞으로 할 일과 이유

확정→발주 경로의 세율/거래유형, 여러 거래처 분리와 미확정 가격, 출력의 실제 파일/파일명·권한·결과 보관을 확인한다. **왜:** 거래처가 채워지고 발주서가 생성돼도 계산 문맥·원본 연결·최종 출력이 모두 보존됐다는 뜻은 아니기 때문이다. 정확한 본문·권한·보존·운영 수락 전까지 P2.3은 완료하지 않는다.
