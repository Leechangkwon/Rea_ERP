# 초기 개발 — 메뉴에서 실제 입력·조회 흐름으로

## 당초 계획과 이유

처음 확인 가능한 계획은 로그인 후 메인과 메뉴를 독립 로컬 샘플로 재현하는 것이었다. 10개 영역·59개 그룹·759개 경로의 계층, 검색·즐겨찾기·최근 메뉴·업무 탭을 먼저 만들었다. **왜:** 사용자가 선택한 시작 범위가 메인/메뉴였고, 아직 확인하지 않은 업무 화면이나 회사 수치를 지어내지 않기 위해서다. 최초 계획에는 공개 배포가 포함되지 않았다.

## 기존 → 변경과 그 이유

- 메뉴 안내 중심 → 재고 전표·양식·자체 API·자체 계정·Self-Customizing 기능군으로 확장했다. 0.6.0 문서는 검증된 계산 커널은 유지하고 명령 경계·인증·권한·저장·설정 적용을 정비했다고 기록한다. **왜:** 화면 접근뿐 아니라 설정이 실제 입력과 저장에 적용되는 흐름을 만들기 위해서다. 모든 코드의 재작성이나 원본 전체 복제를 뜻하지 않는다.
- 공통 구매 화면 → 0.8.0에서 원본의 요청 품목행 거래처, 계획 행별 상태/잔량, 구매의 확인축, 관찰한 입력/조회 배치를 반영했다. **왜:** 단계별 업무 단위가 서로 달라 공통 화면만으로는 행별 연결과 상태를 표현하지 못했기 때문이다.
- 즉시 저장처럼 보이는 원본 계획 목록 → 자체 앱은 명시 변경 저장과 확인을 사용했다. **왜:** 원본 조회 중 변경 자체가 서버 저장이라는 사실을 확인했고, 관찰과 실제 변경을 분리할 필요가 있었기 때문이다. 이 차이는 원본 동등성 완료로 처리하지 않는다.
- 설정 목록 → 0.9.0에서 새 전표에 계산 정책을 명시 복사하고 과거 전표는 기존 정책을 유지했다. **왜:** 표시/기본값 변경으로 이미 저장된 금액과 연결 전표를 재계산하지 않기 위해서다.

## 입력·현황·출력 확장 이력

0.11~0.27의 문서는 검증 도구, 입력 도구, 정렬, 저장 후 유지/신규, 요청 불러오기와 계획→발주 흐름을 나누어 기록한다. 0.28~0.42에는 그래프·필터·색상, 소계·드릴다운, 계획/발주/요청 집계, 집계대상, 거래내역, 조회 열을 차례로 대조했다. **왜 작은 단위로 나눴는가:** 버튼의 존재보다 각 선택·취소·저장·결과 연결을 검증한다는 전역 기준에 맞추기 위해서다. 문서에 없는 개별 버전의 개인적 판단 이유는 재구성하지 않는다.

## 검증 범위와 남은 일

REA 6.4.0에서 공개 JavaScript를 비활성 텍스트로 분석하고 해시·출처·추적 근거를 남겼다. 구문 분석 성공, 정적 호출 후보, 메뉴 수는 서버 실행·금액·권한·저장 동등성의 증거가 아니다. 0.10 재고현황의 합성 수불/CSV/인쇄 확인도 실회사·실기기 검증과 구분한다.

현재 Git은 0.42.0 가져오기부터 시작한다. **이전 세션별 날짜와 전체 대화는 확인되지 않는다.** 앞으로는 P0~P10의 본문·요구사항·합격 기준에 기존 기능을 다시 연결한다. **왜:** 초기 범위의 성공을 전체 ERP 완료로 오해하지 않도록 하기 위해서다.
