# P8 — 그룹웨어·전자결재·업무·CRM·파일·웹메일

## 당초 계획과 먼저 진행한 이유

실제 사용자와 공용 데이터를 기반으로 역할 간 결재, 메일/첨부·백업·동기화 매뉴얼을 검증한다. 로드맵은 공통 기능을 P8까지 무조건 미루지 않고 앞선 업무에 필요한 부분부터 만들도록 정했다. **왜:** 발주서 Email 같은 구매 흐름에도 메일과 권한이 필요하기 때문이다.

## 기존 → 변경과 이유

- 외부 미연결/메일 작성 수준 → 0.45 Gmail 발주 작성/PDF·영속 발송 결과(`a2b8256`)를 연결했다. **왜:** 작성/첨부 미리보기와 실제 전송 결과를 구분해 추적하기 위해서다.
- 발주 전용 경로 → 0.46 개인 메일함·MIME 수신·임시보관/휴지통/복원, 승인된 Cloudflare/SMTP 활성화로 확장했다. **왜:** 보내기만으로는 받은 회신과 보관·복원이 완성되지 않기 때문이다.
- 전송 성공 표시와 실제 도착 차이 → Worker redirect 수정(`5780f5f`) 뒤 실제 도착·양방향을 확인했다(`32367d7`·`9d39c91`). **왜:** 설정/응답 성공만으로 수신함 도착을 증명할 수 없기 때문이다.
- 메일함 설정과 배포 Worker 경로 차이 → 0.47~0.47.2 설정·라우팅 상태 범위·Worker 반영을 보완했다. **왜:** 화면에 저장한 구성이 실제 수신/발신 경로와 일치해야 하기 때문이다.

위 실제 송수신은 **당시 승인과 근거가 있는 작업**이다. 현재 문서 작성에서 발송/회신/설정을 실행한 것은 아니다. 최신 배포 기록은 기존 3함·8통·1첨부 보존을 확인한다.

## 남은 일과 이유

전자결재는 로그인/메뉴 존재와 분리하여 실제 역할 간 요청·확인·승인·반려·위임·보관 계약을 확보한다. **왜:** 일반 전표 수정 권한을 결재 권한으로 간주할 수 없기 때문이다. 확인 권한도 `inventory.write`와 자동 동일시하지 않는다.

CRM/파일·메일템플릿·동기화는 실제 매뉴얼·저장 주체·첨부 보존/권한을 확인한다. **왜:** 개인 메일함이나 브라우저 전표만으로 회사 공용 업무/결재 완료를 입증할 수 없기 때문이다. 두 사용자/두 브라우저와 충돌 처리를 검증하기 전 P8 완료로 올리지 않는다.
