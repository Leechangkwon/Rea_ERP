# P9 — 업로드·API·Excel·모바일·POS·외부연동

## 당초 계획과 현재 상태

각 영역의 실제 계약에 따라 API와 화면의 일치·멱등성, 외부 시스템/장비 결과를 검증한다. 기존 자체 API와 원본 OAPI 참조는 별개다. 자체 API 동작이 실제 ECOUNT 호출/프로토콜 호환 성공을 뜻하지 않는다.

## 업로드의 기존 → 변경과 이유

붙여넣은 값을 바로 업무자료로 취급 → raw를 보존한 분리 staging·수량 환산·공급/세액의 공란/0 구분·독립 검토 모델을 만들고 0.74 읽기 전용 검토 UI에 연결했다. **왜:** 원문을 잃거나 미리 기본값을 넣으면 사용자가 입력한 값과 제안값을 구분할 수 없기 때문이다. 실제 전표 저장은 미완료다.

표시 자릿수를 입력 정책으로 상속 → 0.75~0.77 구매 nullable 정밀도, 선택적 표시 형식, 업로드 입력 정책을 분리했다. **왜:** 보이는 소수 자릿수와 입력 허용 범위/계산/외화 한계는 서로 다른 계약이기 때문이다.

일치하는 이름을 자동 확정 → 0.78 담당자·창고·프로젝트의 코드/이름 제안, 0.79 회사 저장규칙의 명시 initializer/typed-none 제안과 최신 수정번호/날짜 보호를 연결했다. **왜:** 중복 이름·비활성 코드·회사 정책 변화에서 임의 매핑/기본값 적용을 막기 위해서다.

앞으로 실제 저장을 연결하려면 회사별 Flow/setup/dataModel, 전표 묶음·필수항목·금액·부분실패/재시도 계약이 필요하다. **왜 보류했는가:** 날짜+순번 같은 추정 묶음은 서로 다른 전표를 합치거나 중복 저장할 수 있기 때문이다. 저장 버튼이 없어도 검토 기능의 완료 범위는 명시한다.

## 모바일의 기존 → 변경과 이유

요청/발주/구매의 requestList, 계획 전용 목록, 단가 generic 목록이 서로 다른 header/작업행을 사용했다. 0.62 상태줄→검색/양식→상세검색→표→하단 동작의 공통 배치를 도입했다. **왜:** 사용자 신고에서 같은 구매 조회인데 위치·크기가 제각각이고 중간 폭에서 상태 버튼이 세로로 눌리는 문제가 확인됐기 때문이다.

0.69.1 재신고에서는 column flex에 남은 wrap, 보고서로 누출된 fallback grid, 라디오에 적용된 일반 input 크기가 원인이었다. nowrap/selector 범위/보고서 검색행/44px 컨트롤·18px 라디오로 수정했다. **왜 검사를 바꿨는가:** 이전 최소크기/preview shell 검사는 거대 버튼을 통과시켰기 때문이다. 실제 index/app shell 5입력·4현황×7폭/높이의 63상태와 높이 상한·overflow·단축키/초안 보존까지 검사했다.

운영 700px에서 버튼 44~49.6px·검색44px·라디오18px 확인 이력이 있지만 **물리 Android 재시험은 미완료**다. 반응형 Chromium 결과를 실제 기기 결과로 바꾸지 않는다. 후속 모바일 변경은 같은 실제 셸·입력/현황 공통 기준으로 검증한다.

## 외부연동 합격 기준

실제 계약·계정/권한·실패 복구·멱등성·장비 출력과 보존을 확인한다. 합성/localhost 검증과 실제 API/기기 검증을 나눈다. **왜:** 외부 시스템을 호출하지 않은 검사를 송신·호환·기기 합격으로 표시할 수 없기 때문이다.
