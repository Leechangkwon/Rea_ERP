# 운영 — 기존 계정·자료를 보존하며 구성 변경

## 당초 계획 → 현재 운영과 이유

출발점은 buildless HTML/CSS/JavaScript의 로컬 샘플이었다. 과거 문서에 Sites/D1 경로도 남아 있지만, 2026-10-19 사용자가 **기존 로컬·Supabase·Cloudflare와 rea.qaredi.com 유지**를 재확인했다. 이후 실제 개발은 Ubuntu/lck의 `/home/lck/projects/Rea_ERP`, 공개 접속은 기존 Cloudflare Tunnel, 서버 저장은 기존 Supabase 구성을 따른다. **왜 변경했는가:** 사용자가 지정한 실제 운영 대상과 기존 계정·자료를 유지해야 했기 때문이다. 과거 배포 설정 파일을 현재 대상의 근거로 삼지 않는다.

## 실제 변경과 검증

0.43.0은 기존 SQLite와 설정을 백업한 뒤 계정 비밀번호 해시·회사·설정·수정 번호를 대조하여 이관했다(`d0a26ff`). 공개 로그인 화면 확인에 이어 실제 기존 계정 로그인·새로고침 후 세션 유지까지 확인했다(`db383d0`). **왜 단계별로 확인했는가:** 서버 응답과 로그인 화면만으로 기존 사용자가 업무에 들어갈 수 있다는 사실은 입증되지 않기 때문이다.

운영 계정/설정과 브라우저 업무자료, 별도 서버 검증자료의 저장 경계는 계속 분리한다. **왜:** 서버로 계정을 옮긴 사실을 모든 업무자료가 회사 공용 DB로 통합된 것으로 오해하거나 자동 이관하지 않기 위해서다.

## 배포 방식이 달라진 이유

root에는 운영에 합격하지 않은 VAT5 연구가 포함돼 있다. 이후 수정은 실제 운영 릴리스에서 만든 분리 후보에 적용하고, 커밋/push·검사·보존 대조를 마친 후보만 배포했다. **왜:** 작은 결함을 수정하면서 미완료 계산식이나 매핑 후보가 함께 설치되는 일을 막기 위해서다. root 전체 빌드는 현재 운영 배포 절차가 아니다.

## 현재 확인된 상태

0.88.11의 소스는 `958d7ed`, 릴리스는 `e4d01ab`이다. 해당 릴리스 근거는 공개 버전/자산, 기존 로그인·작업탭, 브라우저 8전표/양식, 서버 app30/gateway0 본문·수정번호, 런타임 설정, 메일 3함·8통·1첨부의 보존을 기록한다. 복원은 미리보기만 수행했으며 실제 적용하지 않았다. 과거 자료 변환 거절 뒤 수정/저장 흐름은 localhost 합성 검증이고, 운영에서는 변환창 열기/취소만 확인했다.

이는 **당시 배포의 기록**이며 이번 문서 작성에서 새 운영 검사를 수행한 것은 아니다. 실제 Android·원본 매뉴얼 전체·실업무 저장 합격도 아니다.

## 앞으로 할 일과 이유

공용 업무 저장·두 사용자/두 브라우저·동시 수정·원장/권한 경계를 따로 검증한다. **왜:** 현재 자체 API 검증영역과 브라우저 전표를 다중 사용자 운영 완성으로 볼 수 없기 때문이다. 기능 변경 때마다 기존 자료 보존을 확인하고, 배포가 없는 문서 변경에는 앱 버전을 올리거나 운영을 재시작하지 않는다.
