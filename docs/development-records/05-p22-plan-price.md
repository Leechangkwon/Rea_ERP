# P2.2 — 발주계획·단가요청·비교확정

## 당초 계획과 이유

요청→계획→단가요청→발주→구매의 5단계를 연결한다. 전표/품목 표시, 부분수량·잔량·분할/묶음, 거래처·납기, 확정 가격을 검증한다. **왜:** 중간 화면이 있어도 선택한 공급처/단가/원본행이 최종 발주로 이어지지 않으면 업무 흐름이 완성되지 않기 때문이다.

## 기존 → 변경과 이유

- 품목 중심 연결 → 0.53.1 원본 직전 품목행 참조와 완료 계획 배분 보호. **왜:** 동일 품목의 서로 다른 원본행 또는 묶음 발주에서 이미 완료한 계획에 수량이 다시 배분되는 손실을 막기 위해서다.
- 무제한 선택/불명확한 입고 위치 → 0.53.2 100선택 제한과 입고창고 선택. **왜:** 확인한 선택 계약과 실제 입고 단위를 입력에 반영하기 위해서다.
- 단가 칸 중심 → 비교 상태 모델→불변 비교 스냅샷/백업→읽기 전용 비교표→명시 확정 선택으로 나누어 구현했다(`8002335`·`3eff892`·`b7101ad`·`ad5a1dd`). **왜:** 제안 가격·수취 가격·선택 상태·확정 결과를 구분하고, 보기만 한 값을 확정 저장하지 않기 위해서다.
- 거래처별 입력/회신 상태 누락 → 0.53.4~0.53.7 입력마감/취소, 수취단가 원자 저장, 신규 다중 거래처, 최초 확정의 요청단가 기본 선택. **왜:** 거래처별 진행과 선택이 개별 업무 단위이기 때문이다.
- 확정 결과 단절 → 0.54.0 확정 단가→발주→부분 구매(`e071a5e`). **왜:** 비교표 선택만으로 끝내지 않고 실제 후속 전표/잔량/금액이 이어져야 하기 때문이다.

- 조회 구매처와 생성 구매처가 다름 → 0.88.6 목록/검색/CSV를 생성과 같은 우선순위로 통일(`7406171`). **왜:** 과거 전표 머리 V002와 현재 품목 기본 V001이 다를 때 화면과 생성 결과가 어긋나는 결함을 재현했기 때문이다.
- 같은 세율이면 다른 코드도 합쳐짐 → 0.88.10 묶음 기준에 거래유형을 포함하고 미리보기에 표시(`86bfa91`). **왜:** 세율이 같아도 거래유형 문맥을 잃으면 후속 구매에서 잘못 계산될 수 있기 때문이다.

## 검증과 한계

비교확정→부분 발주→부분 구매의 공급처·원본행·잔량·재고/채무 대사는 합성 근거가 있다. 운영 조회/보존과 원본/운영의 실제 업무 저장 합격은 별개다. 거래처 자동분리·미확정/요청가확정의 모든 저장 분기·유효기간/할인·외부 회신 계약은 미완료다.

## 앞으로 할 일과 이유

최신 큐는 **단가 비교확정→발주 생성의 거래유형·세율 보존을 먼저 대조**하는 것이다. 결함으로 미리 단정하지 않는다. 최소구매단위·수량 산정은 수치 근거를 기다린다. **왜:** 공식 소개 이미지의 선택항목만으로 배수 올림·하한·혼합 변수 산식을 만들 수 없기 때문이다. 보유재고 차감 helper를 전체 계획 계산식으로 확대하지 않는다.
