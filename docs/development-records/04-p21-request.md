# P2.1 — 발주요청 입력·조회·BOM/주문 불러오기

## 당초 계획

요청 입력/조회·확인·연계를 매뉴얼 절차로 검증한다. 요청 품목행의 거래처와 출처를 보존하고 다음 단계가 같은 품목·수량·조건을 사용하게 한다.

## 기존 → 변경과 이유

- 검색 입력 즉시 결과 변경 → 0.48.0 명시 Search 적용과 검색 초안 보존(`46b9766`). **왜:** 편집 중인 검색 조건과 사용자가 실행한 결과 기준을 분리하기 위해서다.
- 단일 참조/불명확한 정렬 → 0.49.0 다중 참조 선택·수정일 정렬, 0.50.0 거래유형 21/22와 관리항목을 연결했다. **왜:** 실제 조회/입력에서 선택 조건과 과세 문맥이 다음 전표로 이어져야 하기 때문이다.
- 생성일만으로 찾는 검색 → 0.51.0 생성/수정 날짜 검색(`bdb71de`). **왜:** 공식 매뉴얼에서 확인한 날짜 기준과 기존 구현의 차이를 줄이기 위해서다.
- 수동 품목 입력 → 0.52.0 BOM 1단계 소요량(`92f927e`), 0.53.0 주문 품목행별 불러오기(`5fb7836`). **왜:** 요청을 기존 주문/BOM에서 만들되 같은 품목이어도 출처·단가·적요 등 업무 조건이 다른 행을 잃지 않아야 하기 때문이다. BOM 전체 다단계/MRP 완료는 아니다.
- 요청 참조가 불명확 → 0.83.0 일반 메모 필드로 편집/검색/저장 연결. **왜:** 단순 참조 문구를 존재하지 않는 외부 관계나 계산 규칙으로 취급하지 않기 위해서다.
- 단일 인쇄만 고려 → 0.86~0.87 선택 요청의 저장 양식별 일괄 인쇄 및 머리 6항목/저장 행 구매처 출력. **왜:** 현재 품목 기본 구매처를 과거 전표 출력에 덧씌우지 않고, 저장된 자료와 양식을 출력해야 하기 때문이다.

## 사용자 신고에 따른 우선순위 변경

0.62.0은 품목의 등록 구매처를 요청 행/불러오기에 반영했다. 이후 0.88.4는 요청에서 발주서로 직접 불러올 때 구매처가 한 곳이면 빈 머리 거래처를 채우도록 수정했다(`a58c754`). **왜 재수정했는가:** 계획 생성에는 있던 기본 반영이 요청 직접 경로에 빠져 실제 저장을 막았기 때문이다. 명시한 거래처는 유지하고 복수/미지정은 임의 선택하지 않는다.

## 검증·남은 일과 이유

요청→계획/직접 발주→부분 구매의 행 출처·잔량·금액·저장/재조회는 합성 검증 근거가 있다. 운영에서는 기존 계정/자료/양식 보존과 안전한 화면 확인을 구분했다. 원본의 전체 오류/권한/설정 저장·업무 수락은 미완료다.

앞으로 구매 5단계 차이표의 요청 조건·BOM/주문 경계·동일 품목 혼합 조건을 실제 본문과 계속 대조한다. **왜:** 불러오기 성공만으로 이후 집계·잔량 연결까지 정확하다고 볼 수 없기 때문이다.
