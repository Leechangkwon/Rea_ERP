# 기초등록 양식의 실제 필드·추가항목·계산식 연결

## 사용자 요청과 원인
2026-10-24 사용자가 기초등록 품목 목록에서 구매처를 선택할 수 없고 문자열/숫자열 추가항목과 계산식을 쓸 수 없다고 지적했다. 화면 재현이 아닌 입력→양식저장→자료저장→조회/CSV→재조회 계약을 구현한다. 기존 PRD/아키텍처/P1의 확장이다.

현재 masterListFields.slice(0,5)로 구매처/상세 필드가 목록의 양식 후보에서 빠진다. 품목 입력의 공통 양식은 단순 masterFields만 등록하고 ItemUI에는 customFields만 넘겨83개 필드의 표시명/읽기전용/기본값 설정과 계산 결과의 실시간 표시가 분리돼 있다. 수식 엔진·안전한 파서·저장 시 재계산은 이미 있으므로 재사용한다.

## 구현 단위
1. ItemCore에 전체83필드의 공통 양식용 정의를 제공한다. 복합 입력형식은 원래 typed 컨트롤을 보존하고 기본값은 변형하지 않는다.
2. 등록 목록은 전 필드와 구매처 코드/명칭을 공급한다. 기본 목록에는 구매처명을 보여주고 사용자 양식은 신규 필드가 자동 노출되지 않게 한다. 과거 c0.. 열 ID는 읽기 시에만 canonical ID로 연결하고 원문/계산식/열 순서를 보존한다.
3. ItemUI는 선택한 입력양식의 전 필드 설정·문자/숫자 추가항목·실시간 계산과 읽기전용·필수 검사를 연결한다. 내장 필드의 신규 기본값을 기존 품목이나 미저장 초안에 소급하지 않는다. 누락된 추가항목의 기본값 처리는 기존 저장 계약을 유지한다.
4. 공통 양식 편집의 기초등록에는 항목 검색, 문자/숫자 추가, 항목 선택/계산식 도우미를 제공한다. 목록의 계산은 보기/CSV용, 입력 양식의 계산은 저장 시 코어에서 다시 검증한다.
5. 기초등록 품목·거래처에서 취소/권한/세션·복합기본값·백업/과거양식 보존, 잘못된 참조/순환/0나눗셈/스크립트 거절을 합성 검증한다.

## 원본 및 배포 경계
공식 FAQ의 구매처 표시·품목 세부 필드·숫자형 사용자 계산식 근거와 현재 소스를 대조한다. 원본 로그인/주 입력행/저장/설정 저장은 하지 않는다. 사용자 요청의 독립 구현과 원본 전체동등성을 구분한다. 운영0.88.15(517cd03)에서 격리 후보0.89.0을 만들고 미배포root VAT5/매핑과 dirty12파일을 보존한다. 관련 검사/전체verify:local/실제셸 브라우저/REA6.4후 커밋·push·기존 WSL/Supabase/Cloudflare 배포·계정/자료/양식/메일 보존을 확인한다. 운영 세션66032 poll/terminate 금지.

## 실제 사용 경로

- 구매처 조회: 품목등록 → 목록 Option → 양식설정 → 양식 항목 검색에 구매처 → 구매처코드/명칭/담당자/연락처/이메일/주소/사업자번호 표시 선택 → 양식명 입력 → 양식 저장·적용. 기본 목록에는 구매처명이 보인다. 기존 사용자 양식은 명시적으로 표시를 켜야 한다. 품목 상세에서 저장된 구매처 코드로만 조회하고 거래처 존재만으로 임의 연결하지 않는다.
- 품목 입력: 품목코드/수정 → 품목 Option → 양식설정 → 상세 필드 검색/항목명·표시·필수·읽기전용·배치 → 문자 항목 추가/숫자 항목 추가 → 계산식 설정 → 계산 대상과 참조 항목 선택/항목 넣기 → 사칙연산·ROUND/MIN/MAX/ABS → 계산식 검사/적용 → 양식명 → 양식 저장·적용 → 품목 값 입력 → 저장(F8). 양식 저장과 품목 저장은 별개다.
- 예: 숫자 사용자 항목을 하나 만들고 `ROUND(buyPrice * extraNumber1, 2)`를 지정하면 입고단가 × 추가숫자항목1을 소수2자리로 계산한다. UI에서 한글 항목명을 골라 넣을 수 있다. 사용자 필드 ID는 자동으로 안정 발급된다.
- 계산을 뺄 때는 해당 숫자 항목의 수식을 비우고 양식을 저장한다. 화면 표시용 계산과 실제 입력 저장의 재계산 범위를 구분한다. 공통 양식은 최대200필드이며 이는 REA 구현 한도다. 원본 이카운트의 한도라고 주장하지 않는다.
