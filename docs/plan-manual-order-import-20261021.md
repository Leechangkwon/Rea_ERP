# 주문 불러오기 라인별 보존 · 0.53.0 계획

## 근거와 차이 정정
원본 발주요청 매뉴얼 EC-HELP-REQUEST-035는 라인별=동일 품목도 행별 유지, 품목별=수량 합산을 명시한다. 2026-10-21 원본 주문서검색창(조회)의 라인별 기본값과 품목별 전환을 관찰했다. 적용·신규·주 입력행 조작·저장은 하지 않았다. 조회 결과가 없어 실제 적용 및 가격 정책은 확인하지 못했다.

앞선 계획의 ‘품목별 수량 합산 부재’는 너무 넓은 판단이다. EntryCore.stageDocuments는 mergeLines를 통해 동일 조건 수량을 이미 합산하고, 서로 다른 조건은 별도 행으로 보존한다. 확인된 결함은 요청의 주문 라인별 불러오기에도 동일 합산이 실행되는 것이다. 원본 공개 코드는 trans_summary_type→summary_type 전달을 확인했으나 서버 집계·단가·거래처·납기 선택 정책은 미확인이다.

## 최소 변경
- 요청 + 주문만 선택 + 내용 복사 + 명시적 라인별에서 원본 선택 행을 합치지 않고 추가한다. 기존 행과도 합치지 않으며 각 행에 고유 lineId와 출처를 남긴다.
- 저장된 전표/양식을 자동 변환하지 않는다. 고유 ID가 없는 기존 전표는 해당 불러오기를 적용한 작성 중 사본에만 ID를 부여하고 명시적 저장을 통해 보존한다. 기존 ID는 유지한다.
- 품목별의 기존 동일 조건 합산/상이 조건 분리, 다른 종류·잔량 연결은 유지한다. UI에 라인별과 품목별의 실제 동작을 설명한다. 전체 원본 동등성 완료로 표시하지 않는다.
- 합성 두 주문의 동일 품목/동일 단가를 라인별2행·품목별1행으로 대조한다. 기존 행, legacy ID, 부분 수량, 출처, 500행 한도, 저장/재조회, 권한·취소·전표/양식 보존을 검사한다.
- 관련 검사→전체 verify:local→REA 좁은 정적 분석→push→보존 백업→기존 운영 반영/조회 확인→보존 대조. 모아는 재로그인 전 대기 기록을 유지하고 가능한 독립 개발을 진행한다.

## 현재 운영 · 0.53.0 요청 주문 라인별 보존

주문을 라인별로 불러올 때 동일 품목도 합쳐지던 문제를 수정했다. 요청+주문 내용복사+라인별에서 선택 행과 기존 입력 행을 각각 보존한다. 품목별의 동일 조건 합산은 기존에 있었으며, ‘합산 부재’라는 이전 차이표를 정정했다. 상이한 단가/거래처/납기 처리의 원본 정책은 미확인이다.

전체 verify:local, 관련Node54(신규6), 브라우저30(신규1) 통과. 원본4범위/자체4함수 REA6.4.0 파싱 성공, 의미coverage unknown/truncated false. 소스5fb7836 push 후 기존 WSL 서버를 재시작했고 공개0.53.0/변경파일 해시·Supabase 정상·익명 접근 차단을 확인했다. 기존 로그인에서 동일 주문을1개씩 두 번 불러와 같은 품목2행으로 유지됨을 확인했다. 저장은 실행하지 않았다.

서버 상태25/0 본문·수정번호, 비공개설정, 메일3함8메시지1첨부가 배포 전후 동일하며 복원미리보기0충돌이다. **브라우저 최종 JSON 대조는 대기**: 작성 중 화면의 닫기 확인 단계 뒤 탭21 입력/포커스 응답이 멈췄다. 대체 탭23은 기존 목록을 표시하지만 백업 버튼이 반응하지 않았다. 원본 전표 저장/발송/실제 복원은 없다. 마지막 브라우저 백업은 배포 전8전표이며 저장 시나리오는 합성 검사다. 모아는 로그인 만료로0.52/0.53 결과 게시·재조회 대기다.
