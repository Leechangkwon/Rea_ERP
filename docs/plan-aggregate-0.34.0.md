# 발주계획 집계 0.34.0

발주계획현황의 집계에서 현재 자체 자료를 최대5축으로 조회합니다. 품목명[규격]·거래처·담당자·창고·프로젝트·그룹·날짜의17축을 지원합니다.

## 사용 예와 합격 조건

품목명[규격]·거래처를 선택하면6열과 첫 축 소계·합계를 표시합니다. 축1개는5열/말단 소계 없이 합계, 축5개는9열/비말단 축4개의 소계입니다. 조건 칸은2개에서 선택 수+2개로 증가해5개까지 늘고 지워도 줄지 않아야 합니다. 초기화는 내역/빈2칸/기본 소계로 돌아갑니다. 미검색 조건이나 조회 오류는 마지막 성공 출력에 섞이지 않아야 하며 읽기 전용 CSV/인쇄는 저장 자료를 바꾸지 않아야 합니다.

## 원본 관찰

원본 발주계획현황의 내역/집계는 기존 구매V56와 다른 legacy 화면입니다. 후보 목록과1·2·5축의 검색 결과를 직접 확인했습니다. 최초2칸, 선택1개→3칸·2개→4칸·3~5개→5칸을 관찰했습니다. 선택 축에는 코드순·방향·소계·지우기 컨트롤이 나타납니다. 5축 결과는 품목명[규격]/거래처/담당자/창고/월별/수량/공급가액/부가세/합계였습니다.

말단 축의 별도 소계는1·2·5축에서 없었습니다. 나머지4축의 제목은 해당 직전 표시값+' 계'였으며 안쪽→바깥쪽으로 나왔고 선택축 전체5칸을 합쳤습니다. 마지막 제목은 합계였습니다. 첫 축 소계를 껐을 때 하위 표시값이 같은 상위 경계가 있었지만 관찰된 하위 소계가 상위 표시값을 가로지르지 않았습니다. 이는 표시값 비교 근거이며 raw SID/서버 GROUPBY 전체를 확인한 것은 아닙니다.

복원 중 CUA30초 시간 초과로 커널이 초기화됐습니다. 기존 탭에 다시 연결해 내역 조회 복귀를 확인했습니다. 이후 조건을 다시 열어 첫 소계 ON도 재확인했습니다. 업무 이름/값/건수·세션 URL을 소스/증빙/실행 자원에 넣지 않았으며 저장/설정 적용/원본 주입력행 조작/출력은 실행하지 않았습니다.

## 실제 REA와 자체 정책

기존82본문에서39참조(기존 실제REA callable37개)를 연결했습니다. V3 후보는 출력폼과 pageOption.aggregateList에서 축을 받고5개 조건 handler를 갖지만 현재 페이지의 실제 control/축 메타·계산기 소비자는 확보하지 못했습니다. 구매의5칸/19축/소계 엔진을 현재 계획의 근거로 삼지 않았습니다. 신규 GET/의미분석 재시도/원문 실행은 없고 common OOM/Flexion timeout도 보존합니다.

자체 계획은 raw 코드로 묶고 기본 코드순/축 방향으로 정렬합니다. 품목은 현재 명칭[규격], 다른 마스터는 현재 명칭/코드 대체를 표시합니다. 그룹과 날짜는 현재 자체 등록/날짜 버킷 기준입니다. 이 표시 포맷/금액 반올림을 원본 서버 동등성으로 주장하지 않습니다. 기존 날짜·납기·거래처·품목·창고·프로젝트·통화·검색 조건을 적용하며 혼합 통화를 거부합니다.

계획 소계는 말단을 생략하고 선택된 전체 prefix의 경계를 유지합니다. 구매의 활성 축만 비교/말단 소계/총합계 정책은 그대로입니다. 직접 호출과 이전 스냅샷에 소계가 없으면 OFF를 유지합니다. 표/CSV/인쇄는 같은 성공 결과를 사용합니다. 계획에 구매 전용 상세 helper가 연결되지 않도록 막고 그래프/비교/명시 정렬도 새로 활성화하지 않았습니다.

독립 검토에서 확정 결함은 없었습니다. 새12개 및 집중/전체 완료 검사 근거는 plan-aggregate/validation.json에 기록합니다. DB와 저장 자료 형식은 바꾸지 않았습니다. 원본 코드순/명칭순 선택·집계대상/양식·주차/거래유형/관리항목·계획 상세·그래프/기간비교·서버/출력 동등성·호스팅 로그인 업무 검증은 남아 있습니다.
