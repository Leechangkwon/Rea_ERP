분석일: 2026-10-15. 원본 회사 자료를 저장하거나 변경하지 않고 공개 배포 JavaScript와 원본 화면의 읽기 전용 조작을 구분해 분석했다.

## 증거와 분석 범위

- 증거: `evidence/entry-rea.json`.
- REA 6.4.0 `analyze_javascript_application` 실제 실행: 공개 번들 4개의 26개 초점 조각, 146,758바이트, JavaScript 4개 파싱, 파싱 실패 0건.
- REA 의미 추적 17개와 기능 추적 4개. 원본 번들의 SHA-256, 추출 구간의 원본 행·열·문자 위치와 별도 SHA-256을 보존했다.
- REA 증거 ID: `ev_6c42f0a48fdd9b698f148761aad7687d92e6f25f72d614df7d151e81c0560f91`.
- 공개 번들 전체의 동작을 분석한 것은 아니다. 추출 범위 밖 의존성과 동적 호출 때문에 의미 그래프의 미확인 항목 3,774개가 남는다. 원본 서버의 계산·저장 계약은 공개 클라이언트 정적 분석으로 확정할 수 없다.
- 원본 전체 소스와 원시 분석 결과는 배포 대상이 아닌 무시된 `.artifacts`에만 보관한다. 이 문서와 증거에는 원본 업무자료·세션값·인증정보를 넣지 않는다.

## 원본과 독립 구현의 경계

안전재고 부족량에 `max(목표재고 - 현재재고, 0)`을 사용하거나 우리 저장 자료로 발주·주문 잔량을 계산한다면, 이는 검증 가능한 우리 ERP 정책이다. 원본 서버가 발주잔량·납기·생산소요 등을 어떤 순서로 반영하는지는 이번 증거로 확정되지 않았다. 화면 모양이 유사한 것과 계산 정책이 같은 것은 따로 검증한다.

`sliplink`의 이름만 보고 전표 수량 불러오기와 같은 기능으로 판단하지 않았다. 이 모듈의 분석된 선택 프로그램은 업무자료·결재·첨부 등 링크 서비스 선택 구조다.

## 합격 조건

1. 전표불러오기는 종류→검색·선택→미리보기→적용 흐름이며, 취소하면 작성 중인 상단·행·조회 위치가 보존된다.
2. 일부 잔량을 불러온 뒤 저장·다시 불러오기·수정·취소에서 원본 행별 잔량이 일관된다. 불러오기만으로 재고나 원본 상태가 변하지 않는다.
3. 재고불러오기를 여러 번 눌러도 입력 품목·수량·단가가 유지되고 재고 표시만 갱신된다.
4. 안전재고는 품목별/창고별, 창고 없음, 음수 재고, 비재고 품목, 품목별 목표와 창고별 목표를 구분해 검증한다.
5. 실제 구현한 할인·바코드·검증은 가상 자료로 결과까지 확인한다. 구현하지 않은 원본 기능을 버튼만 만들어 완료로 표시하지 않는다.
6. jsdom/계산 테스트, 로컬 브라우저, 배포 성공, 배포된 앱 계정 로그인, 원본 UI 관찰은 각각 기록한다.

My품목 저장/관리, 전표바코드, 원본 바코드 수량 대조용 검증, 금액 할인·모든 VAT/반올림 조합, 생산 소요량 불러오기, 이익·금액 조정은 후속 분석·구현 항목이다. 현재 입력 검증은 일반 입력값/잔량 검증이며 원본의 바코드 검증과 다르다. 안전재고 결과에 따른 자동 발주나 저장 금지 정책은 구현하지 않았다. 브라우저 업무자료와 서버 API 업무자료는 기존처럼 별개다.
