# 구매처 기본값·품목 선택/신규와 구매관리 조회 반응형 일관성

사용자 신고3장(13259/13261/13265)과 요청을 최우선으로 진행한다. 기준운영0.61.0/c56d15b, main9f1af5e에는VAT5 미완료 연구가 있으므로 root 전체test/build 금지. 운영 기반 격리후보에서 검증/배포한다. 기존 PRD·아키텍처와 현재 자료/양식/계정/메일 보존. 다른 후속 조건양식 작업보다 이 결함을 우선한다.

## 원인/범위

품목 구매처가 optional이고 요청/계획 신규 행 품목 선택이 item.supplier를 반영하지 않는다. 발주계획 후보에는 기존fallback이 있으나 품목 자체에 구매처가 없으면 결과도 비어 발주 실패한다. 현재 비공개 보존백업은 요청5행/품목4개 모두 구매처 공란. 임의 등록거래처 선택이나 일괄 자료보정은 하지 않는다.

조회는 requestList(요청/발주/구매), PurchasingPlanListUI(계획), generic docList(단가요청)로 나뉘어 header/검색/양식/동작행 위치가 달랐다. 태블릿 중간폭의 head flex:1 상태영역이 검색/양식 고정폭에 눌려 세로열이 됐다. 공통 status 전체행→quick/Search/양식→상세검색→결과→하단동작 구조/class와44px 터치/일관된 간격을 적용한다. 계획의 미구현 양식 UI를 만들어 기능이 있는 것처럼 표시하지 않는다.

## 기능 계약

신규 품목 저장은 등록된 활성 구매처 필수. 기존 구매처 없는 품목의 읽기/백업/일반 수정은 유지하며 기존 값을 자동변환하지 않는다. 기존 구매처를 다른 값으로 변경하면 활성 등록코드 검증. 품목의 구매처는 단일 선택 모달 검색/페이지/취소/적용을 제공하며 모달 내 신규 거래처 등록은 별도 명시 저장으로만 반영한다. 부모 품목 초안과입력값을 보존하고 생성된 거래처만 선택한다. 품목 저장 전까지 새 거래처의 존재/품목의 저장상태를 구분한다. 계정/회사·권한/닫힌창/다른화면·저장원문 CAS 보호를 적용한다.

품목별 행 거래처 명시값 > 구매 계열 전표의 수동/과거 상단 거래처 > 품목등록 구매처 순서. 판매 주문의 고객은 구매처로 상속하지 않는다. 신규 요청/계획의 품목 선택·불러오기·저장/재조회→발주서 생성에 동일하게 적용하고 수동 override/서로 다른품목별거래처를 보존한다. 기존 공란자료는 저장 없이 현재 품목 구매처를 후보에 표시할 수 있으나 원문서를 바꾸지 않는다. 구매처 없는품목은 코드/명칭과 품목등록 보완 경로를 알려주고 임의 거래처로 생성하지 않는다. 한 장 모드도 선택행 구매처가 같은 한곳이면 기본값으로 사용하되 여러곳은 명시 거래처 지정이 필요하다.
