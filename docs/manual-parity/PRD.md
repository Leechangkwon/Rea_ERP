# REA ERP 매뉴얼 기반 기능 재현 PRD

## 현재 선행계약 · 매핑센터 구매 우선 (REQ-COM-MAPPING-001)

기존 매뉴얼은 원본/목표 메뉴 연결뿐 아니라 목표 항목별 원본항목 선택·적용, 목표 입력화면에서 연결 원본전표를 골라 불러오는 결과까지 요구한다. 메뉴 pair 저장은 완료가 아니다. 현재 자체 필드설정버튼 비활성/입력소비자 미연결을 실제 차이로 기록했다. 주문→발주요청 등 기존 구매 불러오기 흐름부터 대조하며 전역759메뉴 지원을 가정하지 않는다.

선행 합격조건은 (1) 실제 source/target 필드·상하단/추가항목·연결 해제/기존매핑 보존 관찰 (2) versioned 설정 저장/재조회·config.write 및 수정번호 충돌·사용중단 (3) 허용 target subset에만 복사해 현재 초안/명시0/빈값/날짜/코드와 기존 source lineage·배분/수량/금액을 보존 (4) 실제셸의 설정→불러오기→저장/재조회/양식·백업 보존이다. 원본이 미확인인 필드 다중결합·기본값/공란/행합산 우선순위는 추정하지 않는다. 신규 구현 전 원본 분리 설정 UI 대조가 필요하며 현 단계는 호환성 분석이다.

업로드의 일반 valid_key_list 설명은 upload 경로로 확장하지 않는 것으로 정정했다. 요청별 실제 설정/Validator 없이는 저장을 계속 차단한다. 근거 `evidence/manual-upload-policy-supplier-20261023.json`.

## BODY 묶음·입력순서 조사 (운영0.82.0 유지)

REQ-COM-FORMS-002의 BODY는 실제 묶음 자식과 입력순서 속성 유무를 확인한 범위만 지원해야 한다. 표시상 한 열/명칭이 원본 묶음의 증거는 아니다. 재정렬은 기존 속성만 갱신하며 회사/조건/메뉴·실제 저장/키보드 합격을 계속 요구한다. 현재는 공통지도와 자체소비자 조사이며 기능 추가/완료가 아니다. 근거 `evidence/manual-request-body-focus-20261023.json`.

## 0.82.0 발주요청 상단 입력순서

발주요청 상단 필드의 입력순서 번호를 표시순서와 별도로 설정하고 명시 저장 때 재정렬한다. 기존 미상 순서metadata는 변환하지 않고 순서이동/재정렬을 막는다. 동일번호 tie/숫자검증은 자체 정책이며 하단/회사공유·다른메뉴와 원본 서버 동등성은 미완료다. 근거 evidence/manual-request-input-order-20261022.json

## 현재 기능 보완 · 0.79.0 회사별 업로드 규칙의 검토 연결

## 이전 보완 · 업로드 저장시값변경 (조사 당시 구현미완료)

실제 요청메뉴에서 확인한 세 규칙은 공란·입력경로 조건을 가진다. 일자·거래유형은 초기값 참조, 외화종류는 직접입력(없음)이며 기본은 기존값유지다. 설정목록의 공란/`-`만 보고 규칙이 없다고 판정하지 않는다. 회사별 원본 설정/최신전표 값을 REA에 복사하지 않는다. versioned 설정/초기값 출처·명시0/공란/없음·원문과 제안값을 분리해 검토 화면까지 연결해야 한다. 예외/묶음/필수/금액/보존/운영저장 합격 전 전체업로드 done은 false다. 목록54/본문23/요구사항26, 운영0.78.0 유지. 세부 실행계획: docs/plan-request-upload-close-20261022.md. 근거 evidence/manual-request-upload-save-rules-20261022.json.

## 1. 목표와 완료 정의

사용자가 이카운트 한국어 매뉴얼에 기재된 업무 절차를 REA에서 수행했을 때 입력 조건, 처리 결과, 연계 전표, 재고/금액, 권한, 출력·보관 결과가 그 매뉴얼과 일치하게 만든다. 현재의 계정·자료·사용자 양식·메일을 보존하며 기존 앱을 확장한다.

**메뉴를 열 수 있음, 화면이 유사함, REA가 소스를 파싱함, 합성 테스트가 통과함만으로 완료하지 않는다.** 전체 완료는 조사 범위를 닫은 매뉴얼 목록의 모든 적용 시나리오가 아래 합격 조건을 충족할 때만 가능하다. 미확인·보류·외부 연결 대기는 실패와 구분하되 완료로 세지 않는다.

## 2. 대상과 범위

한국어 ERP의 관리자·기초자료 담당자·구매/영업/창고 담당자·생산 담당자·회계/급여 담당자·결재자·외부 거래처/직원 사용자를 포함한다. 실제 역할별 권한 범위는 관련 매뉴얼에서 확정한다.

전역 범위는 기초등록, Self-Customizing, 로그인/권한/감사, 구매/발주, 재고/물류/시리얼, 영업/판매/수발주, 생산/외주/MRP/BOM/품질/원가, 회계/자금/세무/자산, 인사/급여/근태, 그룹웨어/전자결재/일정/CRM, 웹메일, 데이터센터/API/엑셀/외부연동, 모바일/POS/출력이다. 메뉴별 교육의 9개 영역과 현재 메뉴 트리 759개를 교차 대조한다. 현재 트리 밖의 매뉴얼 기능도 조사대장에서 빠뜨리지 않는다.

이카운트 자체 서비스 가입·요금·상담, 제3자 계정, 유료 API, 실제 금융/세무 제출, 물리 장비는 적용성·대체 서비스·시험 방법을 별도 판정한다. 자동으로 구현 범위에서 빼거나 가짜 성공으로 치환하지 않는다. 해당 기능의 실제 검증 의존성이 해결될 때까지 미완료다. 기존 실행 환경은 로컬 WSL + Supabase + Cloudflare/rea.qaredi.com이다.

## 3. 현재 기준선

- 운영 릴리스 기록: 0.50.0. 발주요청·계획·발주서·구매의 일부 전용 처리와 원본 대조가 있다.
- 과거 메뉴 분류: 759개 중 메뉴만 487, 공통/자체 처리 251, 부분 전용 21. 이 숫자는 동등성 점수나 현재 전 메뉴 재시험 결과가 아니다.
- 공개 교육목차 551개(기초30·상황별134·메뉴별387), 고유 영상545개를 현재 수집했다. 본문 요구사항 분해는 미완료다.
- 기존 구매실 교육자료의 26절차와 합성 검사 기록을 재사용하되, 원문 부재와 공식 동등성 미검증을 표시한다.
- 계정/회사/설정은 서버 상태, 재고·구매 업무자료는 사용자별 브라우저 저장소, 연동 API는 별도 검증 상태다. 다중 사용자 공동 업무자료와 신원에 근거한 결재는 앞으로 해결해야 한다.
- 현재 거래유형21/22 선택과 관리항목 검색은 일부 구현이다. 회사·품목·창고 세율 우선순위, 관리항목 적용 대상, 원본 서버 정렬/출력/결재를 전체 구현으로 간주하지 않는다.

## 4. 근거 우선순위와 충돌

사용자 요구 → 해당 버전의 공식 매뉴얼·온라인 도움말 → 현재 원본의 안전한 실제 관찰 → REA 공개 정적 코드 분석 → 과거 관찰/사용자 교육자료 순서로 근거를 결합한다. 사용자 요구가 원본과 다르면 자체 요구사항으로 명시하고 원본 동등성 점수와 분리한다. 매뉴얼과 화면이 충돌하면 문서 ID·버전·시각·조건을 기록하고 해결 전 합격 처리하지 않는다.

원본 업무 전표 저장/삭제/발송/설정 저장과 자동 초안을 만드는 행 편집은 하지 않는다. 조회와 별도 팝업, 공식 문서, 정적 코드를 이용한다. 저장 동작의 원본 증거가 부족하면 공식 문서나 허용된 독립 시험 환경으로 보완한다. 실업무자료를 테스트 입력으로 옮기지 않는다.

## 5. 요구사항 분해 형식

각 요구사항은 `REQ-영역-번호`, 출처 문서/개정판/절 또는 영상 시각, 적용 조건, 역할, 사전 자료, 단계별 입력, 기대 UI/저장/연계 결과, 취소·오류·권한 분기, 재조회/새로고침/다른 사용자 결과, 관련 구현/테스트/배포 근거를 갖는다. 수량·금액·날짜·정렬은 비교 가능한 정확한 값으로 쓴다. 매뉴얼에서 확인하지 않은 값은 제안 조건으로 표시한다.

상태 흐름: 목차확인 → 본문검토 → 요구사항확정 → 원본대조 → 설계 → 구현 → 로컬합격 → 운영합격 → 완료. `blocked`는 이유와 다음 해결행동을 갖는 별도 상태다. 목차 항목 하나에 정상·오류·권한 등 여러 시나리오가 대응할 수 있다.

## 7. 기능별 합격 조건

1. 출처와 버전이 있고 단계·기대결과가 확정되어 있다.
2. 매뉴얼의 정상 동작 및 적용되는 취소·오류·권한 조건을 재현한다.
3. 저장 뒤 재조회·새로고침·연결 문서/장부/출력 결과가 기대값과 같다.
4. 합성 자동 검사와 실제 REA 브라우저 검사에 재현 가능한 근거가 있다. 외부 연동은 모의 성공과 실제 결과를 구분한다.
5. 공용 데이터 기능은 권한이 다른 두 사용자·두 브라우저의 공유/차단·동시수정까지 통과한다.
6. 기존 백업의 자료/합계/참조/양식·계정·메일 보존을 검증한다.
7. 배포 버전·커밋·검사 결과·미해결 차이를 기록하고 커뮤니티에서 다시 읽어 확인한다.

전체 완료는 적용되는 모든 요구사항이 1~7을 통과하고 미분해 매뉴얼·미해결 충돌·미검증 외부 의존성이 없을 때다. 접근 못 한 자료를 분모에서 제거하지 않는다. 완료를 위해 범위를 줄여야 한다면 사용자 요구 변경으로 별도 기록한다.

## 8. 공통 품질 기준

- 기존 계정, 비밀번호 해시, 회사·권한·설정, 전표·연결·수량·금액, 양식ID/숨김/기본값, 메일·첨부를 보존한다.
- 자료가 읽히지 않거나 서버와 충돌하면 덮어쓰지 않고 복구/재조회 경로를 제공한다. 마지막 쓰기 우선으로 유실시키지 않는다.
- 서버 권한은 화면 버튼 숨김과 별개로 검사한다. 외부 키는 서버 전용 비공개 설정에 둔다.
- 390px 및 데스크톱에서 핵심 절차를 수행할 수 있게 검증한다. 물리 장비와 실제 모바일은 별도 근거다.
- 숫자 정밀도·반올림·시각/업무일 기준은 요구사항마다 확정한다. 기존 과거 금액을 재계산하지 않는다.
- 성능 합격값은 측정 가능한 시나리오와 데이터량을 먼저 정의한다. 임의의 응답시간 수치를 원본 요구로 주장하지 않는다.

## 9. 진행률과 기록

각 영역에 목차수집 수, 본문검토 수, 요구사항확정 수, 구현 수, 로컬합격 수, 운영합격 수, 최종완료 수, 보류 수를 따로 집계한다. 전체 분모 확정 전 종합 퍼센트를 발표하지 않는다. 기존 합성검사 수·메뉴 수·REA 정적 후보 수를 완료율로 변환하지 않는다.

모아 프로젝트에 PRD, 아키텍처, 매뉴얼 조사/요구사항, 진행일지를 연결한다. 조사·설계·구현·검증·배포·장애 해결의 의미 있는 단계마다 기존 문서를 보존하며 갱신한다. 각 기록은 일시/요구사항ID/변경/근거/결과/남은 차이/다음 순서를 갖는다. 커뮤니티 게시 성공은 저장 후 재조회로 확인한다. 연결 실패 시 로컬 게시대장에 남기며 성공으로 기록하지 않는다.

## 10. 현재 열린 사항
